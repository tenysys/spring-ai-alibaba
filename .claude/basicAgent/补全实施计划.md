# 补全实施计划

## 目标

围绕 `.claude/补全清单.md`，先修通 `basic-agent` 的应用主链路，再补发布快照、绑定快照和扩展能力，最终满足通用智能体设计方案中 `3.1`、`3.2` 的当前落地范围。

## 实施原则

1. 先修错误关联和状态流转，再补新能力，避免在错误数据模型上叠功能。
2. 先保证“每个 agent 只有一个草稿”的一致性，再处理版本切换和发布快照。
3. 运行时一律读取版本快照，不依赖零散表实时拼装。
4. 资源绑定快照统一复用 `AgentResourceBindingService`，不重复造查询逻辑。
5. 配置项统一落在 `framework` 模块，避免魔法数字散落在业务代码中。

## 第一阶段：修通版本主链路

### 1. 实体与查询修正

1. 修正 `AgentAppVersionEntity` 的使用方式，确保所有版本查询按 `agentId` 维度取数。
2. 修正获取最新草稿、最新发布版、指定版本、发布目标版本的查询条件。
3. 修正版本列表查询从 `like(agentId)` 改为 `eq(agentId)`。

### 2. 草稿模型收敛

1. 创建应用时自动生成初始草稿，版本号为 `1`。
2. 保存版本接口改为按 `agentId` 驱动，不再强依赖版本 `id`。
3. 未发布前始终更新当前草稿，不新建额外草稿。
4. 已发布后首次编辑时，从当前发布版复制出草稿。
5. 已有草稿时继续保存只更新该草稿，不递增版本号。

### 3. 版本号规则落地

1. 统一实现“下一个版本号”生成器。
2. 规则区分两种场景：
   - 更新现有草稿：沿用当前草稿版本号
   - 新建草稿：生成下一个版本号
3. 前端展示统一由后端返回数值版本或格式化后的 `v{version}` 约定支持。

### 4. 状态机修正

1. 应用状态流转修正为 `DRAFT -> PUBLISHED -> PUBLISHED_EDITING -> PUBLISHED`。
2. 版本状态保证同一时刻只有一个 `DRAFT`。
3. 发布动作只作用于当前草稿，并保留历史发布版本。

### 5. 版本切换能力

1. 新增查询最近已发布版本列表的能力。
2. 新增“版本切换”接口和 service。
3. 版本切换规则：
   - 目标版本必须是 `PUBLISHED`
   - 只能落在最近 `publishedVersionHistoryLimit` 个已发布版本内
   - 有草稿时覆盖草稿内容，不改当前草稿版本号
   - 无草稿时新建草稿，版本号递增

### 6. 配置落地

1. 在 `framework` 模块新增 `BasicAgentProperties` 或等价配置类。
2. 增加 `nrec.basic-agent.published-version-history-limit=20`。
3. 接入 Spring `@ConfigurationProperties` 管理。

### 7. 接口和返回修正

1. 修正 `AgentAppVO` 返回 `id`。
2. 补齐版本查询、保存、发布、切换的参数校验和异常提示。
3. 统一控制器命名和语义，确保“应用保存”和“版本保存”边界清晰。

## 第二阶段：补齐发布快照

### 1. AgentConfig 快照模型

1. 参考设计方案中的 `AgentConfig` 结构设计 `config` 快照。
2. 至少覆盖：
   - `Parameter`
   - `Memory`
   - `PromptVariable`
   - `KnowledgeConfig`
   - `DatasourceToolConfig`
   - `McpBindingConfig`
   - `ComponentBindingConfig`
3. Dify 知识库检索配置纳入第二阶段范围，`DifyRetrieveRequest.retrieval_model` 至少支持：
   - `search_method`
   - `top_k`
   - `score_threshold_enabled`
   - `score_threshold`
   - `reranking_enable`
   - `reranking_mode`
   - `reranking_model.reranking_provider_name`
   - `reranking_model.reranking_model_name`
   - `weights.weight_type`
   - `weights.keyword_setting.keyword_weight`
   - `weights.vector_setting.embedding_provider_name`
   - `weights.vector_setting.embedding_model_name`
   - `weights.vector_setting.vector_weight`
4. 形成统一 JSON 快照对象，供发布态直接使用。

### 2. 绑定快照固化

1. 发布时通过 `AgentResourceBindingService` 拉取智能体当前绑定资源。
2. 第一阶段绑定快照覆盖：
   - 知识库绑定
3. 将绑定结果和必要元数据一并写入版本快照。

### 3. 发布态读取策略

1. 正式运行固定读取发布版本快照。
2. 调试态读取最新草稿；没有草稿时读取最新可编辑内容。
3. 禁止运行时回查零散绑定表来拼正式配置。

## 第三阶段：补齐扩展能力

### 1. 资源绑定恢复抽象

1. 补齐“发布快照配置 -> 资源绑定实体”的反向恢复能力，形成统一恢复入口，避免版本切换、复制应用分别手写资源绑定迁移逻辑。
2. 恢复抽象需要面向通用资源配置结构设计，能够根据快照中的资源配置段反推出：
   - `AgentResourceBinding`
   - `AgentResourceBindingItem`
   - 必要的 `resourceId / resourceType / metaData / params / items`
3. 当前阶段实际落地范围只实现知识库资源，但恢复接口、快照结构和转换模型必须保留扩展到 `DATASOURCE / MCP / SKILL / AGENT` 等资源类型的能力。
4. 明确分层职责：
   - `AgentVersionSnapshotService` 负责从快照中提取资源配置
   - `AgentResourceBindingService` 负责把资源配置转换成绑定请求，并执行绑定落库与覆盖
5. 在 `AgentResourceBindingService` 中增加“按目标 agent 全量对齐某类资源绑定”的能力，支持根据快照内容完成新增、覆盖、删除，而不是只做单条追加绑定。

### 2. 切换版本补齐资源覆盖

1. 保持现有“切换历史已发布版本 -> 生成或覆盖当前草稿”的行为不变，不直接上线。
2. 在版本切换成功定位目标发布版本后，除覆盖草稿 `description/config` 外，还要读取目标发布版本快照中的资源配置，并恢复目标版本对应的资源绑定。
3. 恢复顺序固定为：校验目标版本 -> 覆盖草稿内容 -> 解析资源配置 -> 对齐目标 agent 资源绑定，保证草稿内容和绑定资源来源于同一历史版本。
4. 当目标发布版本快照中某类资源配置为空时，需要清空当前 agent 该类资源绑定，保证切换结果与目标发布态一致，而不是保留旧绑定。
5. 当前阶段切换版本实际恢复知识库绑定；实现方式不能写死在版本服务里，应通过通用恢复抽象分发到知识库恢复器。

### 3. 复制应用与资源关系迁移

1. 新增复制应用接口，复制结果是“新创建一个智能体应用”，应用实体信息与源应用保持一致，但拥有新的应用 `id`。
2. 复制版本来源固定为源应用“最新发布版本”，不复制当前草稿；新应用创建后生成一份草稿版本，草稿内容来自源应用最新发布版本。
3. 复制后的版本状态为 `DRAFT`，不是 `PUBLISHED`；其 `description/config` 取源应用最新发布版本的可编辑内容。
4. 复制应用时需要同步迁移源应用最新发布版本对应的资源绑定关系，但迁移方式不是复制原绑定主键，而是针对新 `agentId` 重新生成一套绑定实体。
5. 资源迁移统一走“快照配置 -> 绑定实体/请求 -> 绑定服务执行”的恢复链路，确保复制和版本切换共用同一套恢复逻辑。
6. 当前阶段复制应用实际迁移知识库绑定；实现上仍按通用资源配置结构设计，为后续资源类型扩展预留入口。
7. 如果源应用没有最新发布版本，则复制失败并返回明确异常，不允许基于未发布草稿复制。
8. 复制完成后，新应用仍遵循“同一 agent 只有一个草稿”的约束，且资源绑定与源应用最新发布版本保持一致。

## 第四阶段：测试与验收

### 1. 单元/集成测试

1. 创建应用自动生成唯一草稿，初始版本号为 `1`。
2. 未发布前反复保存只更新同一草稿，版本号不变。
3. 已发布后首次保存复制发布版生成草稿，版本号递增。
4. 已发布后继续保存仍更新同一草稿，版本号不变。
5. 发布后能正确读取当前发布版。
6. 版本切换只允许最近 `N` 个已发布版本。
7. 版本切换到已有草稿时仅覆盖内容，不改草稿版本号。
8. 版本切换后无草稿场景会创建新草稿并递增版本号。
9. 发布快照包含资源绑定信息。
10. 资源恢复器能够根据发布快照中的资源配置反推出绑定请求或绑定实体；当前阶段至少覆盖知识库配置。
11. 版本切换到历史发布版时，会同步恢复该发布版对应的知识库绑定；若目标快照无知识库配置，则会清空当前知识库绑定。
12. 复制应用时会创建新的应用实体，并基于源应用最新发布版本生成新的草稿版本，不复制源应用当前草稿。
13. 复制应用后，目标应用的知识库绑定是按新 `agentId` 新建的一套绑定关系，但绑定内容与源应用最新发布版本一致。

### 2. 验收标准

1. 同一 `agent` 任意时刻只有一个 `DRAFT`。
2. 所有版本查询都以 `agentId` 为主维度，不串数据。
3. 版本切换不直接上线，只生成或覆盖当前草稿。
4. 发布态配置可以仅依赖版本快照完成运行。
5. 最近已发布版本数量限制可通过 `framework` 配置项调整。
6. 资源迁移逻辑不依赖人工回查零散绑定表拼装，而是能够基于发布快照中的资源配置恢复绑定关系。
7. 回滚式重发版后，草稿内容与资源绑定必须同时回到同一历史发布版本；当前阶段至少保证知识库绑定一致。
8. 复制应用后，新应用的初始草稿与资源绑定来源于源应用最新发布版本，而不是源应用当前编辑态；当前阶段至少保证知识库绑定一致。

## 建议执行顺序

1. 先完成第一阶段，再进入第二阶段。
2. 第二阶段完成后补第三阶段扩展能力。
3. 每阶段结束后执行一次针对该阶段的回归测试，再进入下一阶段。

# 智能体实现方案（结合版）

## 1. 文档目标

本文档用于给出 `data-agent-service` 中通用智能体的可落地实现方案。

目标不是简单复制 `spring-ai-alibaba-admin` 中的 `BasicAgent`，也不是推翻 `data-agent-service` 现有三层模块，而是：

```text
迁移 BasicAgent 的应用层与执行层设计
  + 复用 data-agent-service 的模型、向量、Dify、数据源、MCP、资源管理能力
  + 在 basic-agent 模块中形成独立的通用智能体实现
  + 保证 common / framework / capability-component 旧接口兼容
```

本文覆盖三部分内容：

- 功能实现方案
- 实体设计方案
- 数据表设计方案

并明确区分：

- 哪些内容从 `BasicAgent` 迁移
- 哪些内容结合 `data-agent-service` 和 `BasicAgent` 实现
- 哪些内容由 `data-agent-service` 保留并直接复用

## 2. 实现原则

### 2.1 总体原则

通用智能体在 `basic-agent` 模块下实现，`common`、`framework`、`capability-component` 作为底层能力层保留。

实现时遵循以下原则：

- 旧接口兼容：不修改现有模块对外语义，不破坏既有调用方
- 新增优先：通过新增模块、适配层、Facade、Executor 承载智能体能力
- 单系统实现：`data-agent-service` 不引入 `workspace` / `tenant` 维度，智能体、版本、组件、会话、运行日志均直接按系统内全局业务 ID 管理
- 运行时收敛：调试态与发布态最终都收敛为统一的 `AgentConfig` 运行时视图
- 资源化配置：将业务资源和配置资源统一纳入智能体装载体系
- 模块解耦：不把通用智能体的应用层逻辑硬塞进 `capability-component`

### 2.2 模块定位

建议最终模块职责如下：

```text
basic-agent
  -> 通用智能体应用层
  -> 通用智能体运行时层
  -> 资源装载与执行编排层

common
  -> 模型工厂、通用枚举、基础 DTO、LLM 工具类

framework
  -> Spring 配置、线程池、AOP、向量底座、配置属性

capability-component
  -> Dify 知识能力
  -> 数据源与 SQL 能力
  -> MCP / 技能 / 资源管理能力
  -> 向量服务与混合检索能力
```

## 3. 总体架构

建议将通用智能体拆成四层：

```text
智能体应用层
  -> 智能体定义、版本、发布、调试、装载配置

智能体运行时层
  -> AgentRequest / AgentResponse / AgentContext
  -> BasicAgentExecutor
  -> Prompt 组装
  -> Tool Calling
  -> 流式与非流式执行

能力适配层
  -> 模型适配
  -> Dify 知识适配
  -> 数据源工具适配
  -> MCP 工具适配
  -> 组件工具适配
  -> SKILL 上下文适配
  -> 记忆适配

底层能力层
  -> common / framework / capability-component
```

建议保留 `basic-agent/pom.xml` 当前依赖方向：

- 依赖 `framework`
- 依赖 `capability-component`

必要时由 `framework` 继续间接提供 `common` 能力。

## 4. 功能实现方案

## 4.1 智能体应用管理

### 功能说明

通用智能体首先是一个应用，需要支持：

- 创建
- 编辑
- 查询详情
- 查询列表
- 调试运行
- 发布
- 查看版本
- 回滚式重发版
- 发布为应用
- 发布为工具/组件

### 实现归类

- 从 `BasicAgent` 迁移
  - `AppEntity` / `AppVersionEntity` 设计思想
  - `latestVersion / publishedVersion` 双视图
  - 调试态与发布态分离
- 结合实现
  - 在 `basic-agent` 中实现智能体应用服务
  - 资源装载使用 `capability-component` 的资源绑定能力
- data-agent-service 保留
  - 现有资源管理、数据源、MCP、知识管理接口不变

### 建议服务

- `AgentAppService`
- `AgentAppVersionService`
- `AgentPublishService`
- `AgentDebugService`

## 4.2 智能体版本管理

### 功能说明

版本管理采用“应用主表 + 版本快照表”模式：

- 创建应用时生成初始草稿版本
- 未发布前更新只修改 `latest draft`
- 已发布后更新基于发布版复制出新草稿
- 发布时将 `latest draft` 提升为 `published`
- 正式运行始终读取 `published`
- 调试运行读取 `draft`

### 实现归类

- 从 `BasicAgent` 迁移
  - 版本控制语义
  - 草稿/发布态隔离
- 结合实现
  - 版本快照中固化业务资源与配置资源装载结果
- data-agent-service 保留
  - 不改现有底层资源表结构语义

## 4.3 智能体运行协议

### 功能说明

统一运行协议建议包括：

- `AgentRequest`
- `AgentResponse`
- `AgentContext`
- `ChatMessage`
- `ToolCall`
- `Usage`

支持：

- 文本对话
- 多轮对话
- 多模态输入
- Tool Call 中间态输出
- 流式与非流式返回

### 实现归类

- 从 `BasicAgent` 迁移
  - 请求/响应/上下文对象模型
  - Tool call 返回模型
- 结合实现
  - 对接 `data-agent-service` 现有 Result、向量、Dify、数据源能力
- data-agent-service 保留
  - 现有各业务 DTO 不改，Agent 层新建协议并做适配

## 4.4 智能体配置模型

### 顶层配置建议

智能体统一配置对象建议命名为：

- `AgentConfig`

建议包含以下配置：

- `modelProvider`
- `model`
- `modalityType`
- `instructions`
- `parameter`
- `memory`
- `promptVariables`
- `knowledge`
- `tools`
- `mcpServers`
- `agentComponents`
- `workflowComponents`
- `skills`
- `filters`
- `fallbackReply`
- `prologue`

### 与原始 BasicAgent 的差异

`BasicAgent` 原始实现中的 `fileSearch` 建议在本项目中改为 `knowledge`，原因是当前方案明确：

- 知识库只通过 Dify 接入
- 向量服务不再直接等价为知识库检索
- 向量能力主要留给长期记忆、工具检索、资源向量化等内部场景

因此建议：

```text
BasicAgent.fileSearch
  -> 在本项目中收敛为 AgentConfig.knowledge
```

### 实现归类

- 从 `BasicAgent` 迁移
  - `AgentConfig` 总体结构
  - `parameter` / `memory` / `promptVariables`
- 结合实现
  - `knowledge` 改造为 Dify 专用知识配置
  - 新增 `skills`、`filters`、`fallbackReply`
- data-agent-service 保留
  - 模型配置数据源、Dify 服务、资源绑定底座继续保留

## 4.5 模型能力

### 功能说明

每个智能体可独立选择：

- 模型提供方
- 模型名称
- 运行参数

支持参数：

- `maxTokens`
- `temperature`
- `topP`
- `repetitionPenalty`

### 实现策略

当前 `data-agent-service` 中：

- [DynamicModelFactory.java](I:/java/workplace/data-agent-service/common/src/main/java/com/nrec/service/common/service/aimodelconfig/DynamicModelFactory.java)
- [AiModelRegistry.java](I:/java/workplace/data-agent-service/common/src/main/java/com/nrec/service/common/service/aimodelconfig/AiModelRegistry.java)

更偏“平台激活模型”。

通用智能体中建议新增：

- `AgentModelFacade`
- `AgentChatClientFactory`

实现方式：

- 优先复用 `DynamicModelFactory`
- 新增“按智能体配置直接创建 ChatModel / EmbeddingModel”的入口
- `AiModelRegistry` 保留为默认模型兜底，不再作为唯一入口

### 实现归类

- 从 `BasicAgent` 迁移
  - `modelProvider + model + chatOptions` 的运行思路
- 结合实现
  - 复用 `DynamicModelFactory`，扩展为智能体级模型装配
- data-agent-service 保留
  - `AiModelRegistry`、现有激活模型机制、Embedding Bean 代理继续保留

## 4.6 Prompt 模板与变量

### 功能说明

系统提示词由：

- `instructions`
- `promptVariables.defaultValue`
- 请求时 `promptVariables` 覆盖值

共同生成。

要求：

- 请求只能覆盖已声明变量
- 支持默认值
- 支持知识库场景下延迟渲染

### 实现建议

可直接借鉴 `BasicAgentExecutor.buildInstructions(...)` 的机制：

- 普通场景：直接 `SystemPromptTemplate.createMessage(...)`
- 知识场景：先保留模板，后由知识增强 advisor 注入 `{documents}` 再渲染

### 实现归类

- 从 `BasicAgent` 迁移
  - PromptVariable 定义方式
  - 默认值 + 请求覆盖机制
  - 延迟渲染机制
- 结合实现
  - 与 Dify 知识增强集成
- data-agent-service 保留
  - 通用 JSON / 文本工具类继续复用

## 4.7 短期记忆

### 功能说明

短期记忆用于多轮会话连续性。

启用条件建议保持与 `BasicAgent` 一致：

- 应用类型为 BASIC_AGENT
- `memory.dialogRound > 0`
- 请求存在 `conversationId`

### 实现建议

迁移 `ConversationChatMemory` 思路，在 `basic-agent` 中实现：

- `ChatMemory` 接口适配
- Redis 持久化
- `conversationId = agentId + "_" + requestConversationId`

建议修正原始实现中的一个问题：

- 读取记忆时应按 `dialogRound` 精确裁剪，不保留 `FIXME`

### 实现归类

- 从 `BasicAgent` 迁移
  - `MessageChatMemoryAdvisor`
  - 会话 key 规则
- 结合实现
  - Redis 依赖复用项目当前基础设施
  - 修复 `dialogRound` 只做开关、不做裁剪的问题
- data-agent-service 保留
  - 现有 Redis 能力和 Spring 配置保留

## 4.8 长期记忆

### 功能说明

长期记忆不是 BasicAgent 当前现成能力，但在设计文档中已明确是通用智能体需要补的能力。

建议采用：

- 对话总结
- 记忆抽取
- 向量化存储
- 相关记忆召回

### 实现策略

长期记忆不走 Dify，建议基于：

- [VectorStoreServiceImpl.java](I:/java/workplace/data-agent-service/capability-component/src/main/java/com/nrec/service/capability/service/vector/VectorStoreServiceImpl.java)

新增：

- `LongTermMemoryService`
- `MemorySummaryService`
- `MemoryRetrieverService`

写入逻辑：

- 触发总结任务
- 生成记忆文本
- 存入向量库

读取逻辑：

- 基于当前 query 检索相关记忆
- 注入到上下文增强层

### 实现归类

- 从 `BasicAgent` 迁移
  - 无直接现成实现，保留其记忆分层思想
- 结合实现
  - 基于 `data-agent-service` 向量能力实现长期记忆
- data-agent-service 保留
  - 向量存储与检索底座继续保留

## 4.11 数据源工具能力

### 功能说明

这是 `data-agent-service` 最有特色的通用智能体能力之一。

目标是把数据源从“管理对象”提升为“智能体工具能力”，支持：

- 绑定数据源
- 选择允许表/概念/字段
- 自动生成工具 schema
- 执行元数据查询
- 执行受控 SQL 查询

### 实现策略

复用现有：

- [DatasourceServiceImpl.java](I:/java/workplace/data-agent-service/capability-component/src/main/java/com/nrec/service/capability/service/datasource/impl/DatasourceServiceImpl.java)
- `DatasourceMetadataService`
- `DatasourceRelationService`
- `DatasourceSemanticService`
- `SqlExecutor`

新增：

- `DatasourceToolCallback`
- `DatasourceToolSchemaBuilder`
- `DatasourceToolSecurityPolicy`

要求：

- 智能体层不直接暴露全量 SQL 能力
- 通过绑定项限制可访问范围
- 输出结构统一封装为 Tool result

### 实现归类

- 从 `BasicAgent` 迁移
  - Tool callback / tool schema / tool result 编排模式
- 结合实现
  - 用 `data-agent-service` 数据源底座实现智能体专属 datasource tool
- data-agent-service 保留
  - 数据源 CRUD、测试连接、元数据采集、连接池、执行器全部保留

## 4.14 SKILL 能力

适用内容：

- 专业规则

### 实现策略

建议新增：

- `SkillDefinition`
- `SkillBinding`
- `SkillContextAssembler`

运行时接入位置：

```text

  + knowledge context
```

### 实现归类

- 从 `BasicAgent` 迁移

- 结合实现

- data-agent-service 保留

## 9. 最终结论

本方案的正确落地方式不是“复制一套 BasicAgent”，而是：

```text
在 basic-agent 模块中迁移 BasicAgent 的应用层与执行层
  -> 用 AgentConfig + AgentVersion + Executor 建立通用智能体框架

在能力接入层适配 data-agent-service
  -> 模型走 common
  -> 基础装配走 framework
  -> Dify / 数据源 / MCP / 向量 / 资源走 capability-component

旧模块继续保持原有职责与对外语义
  -> 通用智能体作为新增能力平行接入
```

这样可以同时满足：

- 通用智能体产品化
- data-agent-service 底层能力复用
- 旧接口兼容
- 后续扩展 SKILL、长期记忆、治理能力的可持续演进

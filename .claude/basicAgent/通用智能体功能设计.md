
智能体配置：包括智能体配置、发布、过滤、日志和监测
- 配置：涉及模型、提示词、知识、工具、记忆、回复的设置，模型支持选择模型设置对应的temperature、topK、topP、最大token数、是否思考，提示词支持自定义变量和ai优化，知识支持智能体绑定dify中的知识库，工具支持智能体绑定MCP服务（需要支持选定具体的MCP工具，默认全选）、智能体、工作流和数据源（需要选定数据源中具体的表或者概念及其属性），记忆支持短期记忆（上下文中的多轮对话轮数）和长期记忆（ai定时总结多轮对话信息，提取核心要素），回复支持智能体无法解答时返回固定内容。
- 发布：包括调用方式和发布方式，调用方式支持通过api进行调用，发布方式分为发布为应用和发布为工具，发布为应用指发布到智能体管理界面（最终的产品形式），发布为工具指发布到能力组件系统（作为其他智能体的工具进行使用）。
- 过滤：支持数据干预和规则干预，数据干预是配置指定问题的回答（可以从已有的问答对话中提取），如果用户问题相似用指定回答回复；规则干预是对输入和输出中的敏感词采用正则表达式匹配替换为固定话术
- 日志：记录智能体在调试和运行时对话记录，每个日志记录支持整个智能体流程的跟踪
- 监测：展示该智能体的运维信息，概览指标包括会话数、使用人数、失败次数、首包延时，详细指标通过折线图显示数据变化。

## 1. 问答/通用智能(BasicAgent)的功能定位

`BasicAgent` 可以理解为一种面向对话式智能体场景的基础应用类型。
目标是：

```text
接收用户输入
  -> 结合系统提示词、历史上下文、知识库、记忆、SKILL与可调用能力
  -> 选择合适模型
  -> 生成回答
  -> 必要时调用外部能力
  -> 返回最终结果
```

支持装载的资源：
- 模型
- 模板与模板变量
- 记忆
- 知识库
- 插件（http接口）
- MCP
- 组件（发布为工具的agent和workflow）
- SKILL

`BasicAgent`定义：
```text
一个以模型为核心
  + 以提示词为控制入口
  + 以知识库/记忆/SKILL为上下文增强
  + 以插件/MCP/组件为外部执行能力
的通用智能体
```

## 2. BasicAgent自身核心功能

### 2.1 应用管理功能

`BasicAgent` 首先是一个应用，因此具备应用层面的基本能力：

- 创建
- 编辑
- 查询
- 发布（发布api、工具、产品）
- 版本管理

这些功能的目标是把“智能体配置”和“对外生效配置”分离开来，使智能体既能持续编辑，也能稳定对外提供服务。

### 2.2 版本控制功能

`BasicAgent` 的配置不是单份覆盖式存储，而是版本化管理。

版本控制的功能价值包括：

- 保留历史配置快照
- 支持草稿态调试
- 支持发布态运行
- 支持在已发布基础上继续编辑

从功能语义看，`BasicAgent` 至少区分两类版本视角：

- 最新编辑版本
- 当前对外发布版本

这样可以保证：

- 编辑不会直接影响线上生效结果
- 发布才代表正式切换生效配置

### 2.3 调试与正式运行分离

`BasicAgent` 的一个重要功能设计是区分：

- 调试运行
- 正式运行

这意味着：

- 草稿配置可用于试运行和验证
- 发布配置才用于正式服务调用

其功能价值在于：

- 降低配置修改带来的风险
- 支持在上线前验证 prompt、工具、知识库和模型行为

### 2.4 多轮对话能力

`BasicAgent` 的基本交互单位是对话消息。

支持：
- 单轮问答
- 多轮上下文对话
- 用户消息、系统消息、助手消息的组合
- 文本与多模态输入

### 2.5 工具调用能力

`BasicAgent` 除了直接回答问题，还具备“在回答过程中调用外部能力”的功能。

这使它不仅可以：

- 基于已有知识生成文本

还可以：

- 获取外部数据
- 调用业务系统
- 复用其他 agent/workflow 能力

因此 `BasicAgent` 在功能上属于：

```text
可执行型智能体
而不只是生成型智能体
```

### 2.6 流式与非流式响应

从能力设计上，`BasicAgent` 支持两类响应方式：

- 非流式响应
- 流式响应

功能区别在于：

- 非流式更适合一次性返回最终结果
- 流式更适合边生成边展示，以及在工具调用中逐步反馈过程

这使 `BasicAgent` 可以同时适配：

- API 同步调用场景
- 前端实时交互场景

## 3. 模型功能

### 3.1 功能定位

模型是 `BasicAgent` 的核心推理资源。

它解决的是：

- 由谁来理解输入
- 由谁来决定是否调用能力
- 由谁来生成最终回答

模型能力本身不是单一模型名，而是两层概念：

- provider
- model

### 3.2 provider 的功能语义

provider 表示模型服务来源。

它在功能层面负责：

- 指定模型服务平台
- 提供访问凭证
- 提供服务地址
- 约束可支持的模型类型

因此 provider 更像“模型资源连接配置”。

### 3.3 model 的功能语义

model 表示具体要调用的模型名称。

它在功能层面负责：

- 决定具体模型能力
- 影响模型质量、速度、成本和上下文容量

因此：

- provider 决定“连谁”
- model 决定“用谁”

### 3.4 模型参数功能

`BasicAgent` 支持配置生成参数，以改变模型输出风格与控制强度。

典型功能包括：

- 最大输出长度控制
- 随机性控制
- 采样范围控制
- 重复惩罚控制
- 是否思考

## 4. 模板与模板变量功能

### 4.1 模板功能定位

模板功能主要用于定义 `BasicAgent` 的系统提示词。

它解决的是：

- 智能体应该如何说话
- 智能体应该遵循什么规则
- 智能体在当前业务中扮演什么角色

### 4.2 模板变量功能定位

模板变量用于让系统提示词具备动态性。

它解决的是：

- 不同请求需要注入不同上下文
- 不同租户/用户/场景需要不同提示词参数
- 让提示词模板能够复用，而不是每次都写死

因此模板变量的功能价值在于：

- 让提示词参数化
- 让提示词具备运行时定制能力

### 4.3 默认值与运行时值

模板变量在功能上分成两层：

- 配置默认值
- 请求覆盖值

其语义是：

- 配置定义有哪些变量，以及默认怎么填
- 请求决定本次调用是否覆盖默认值

这样既能保证模板可复用，也能满足单次调用的定制需求。

## 5. 记忆功能

### 5.1 功能定位

记忆功能用于支持跨请求保留会话上下文。

它解决的是：

- 模型如何记住之前聊过什么
- 用户在后续提问时如何延续上下文
- 智能体如何形成连续会话体验

### 5.2 记忆的功能边界

记忆的主要边界是“会话级上下文延续”，而不是业务知识库。

它更适合承载：

- 近期对话历史
- 当前会话中的用户偏好
- 当前会话中的任务状态

它不适合替代：

- 长期结构化知识管理
- 文档检索型知识供给

### 5.3 记忆与前端历史消息的区别

在功能层面，前端传历史消息和后端记忆不是同一件事。

前端历史消息表示：

- 本次请求显式提交的上下文

记忆表示：

- 系统根据会话标识自动补回的历史上下文

因此两者的区别是：

```text
前端历史消息
  -> 本次请求主动携带

记忆
  -> 系统自动延续
```

## 6. 知识库功能

### 6.1 功能定位

知识库功能用于为 `BasicAgent` 提供外部事实与文档支持。

它解决的是：

- 模型自身不知道的业务知识从哪里来
- 回答是否能基于指定文档资料
- 如何提升事实准确性与可追溯性

因此知识库本质上是：

```text
面向文档与事实的上下文增强能力
```

### 6.2 知识库与记忆的区别

知识库与记忆虽然都能补充上下文，但功能边界完全不同。

知识库侧重：

- 文档资料
- 事实召回
- 外部知识支持

记忆侧重：

- 会话历史
- 当前对话延续
- 用户交互上下文

可理解为：

```text
知识库
  -> 我有哪些资料可以查

记忆
  -> 我们之前聊过什么
```

### 6.3 知识库的功能元素

知识库能力通常包含以下功能元素：

- 选择知识库范围
- 控制是否开启检索
- 控制是否返回引用信息
- 控制召回数量
- 控制相似度阈值
- 控制是否重排

## 7. 插件功能

### 7.1 功能定位

插件功能用于把外部 HTTP/OpenAPI 能力接入 `BasicAgent`。

它解决的是：

- 智能体如何访问外部业务系统
- 智能体如何执行标准化 API 调用
- 智能体如何从外部接口获取结构化结果

因此插件本质上是：

```text
外部 API 能力入口
```

### 7.2 插件能解决的典型问题

插件适合承担：

- 查询外部系统数据
- 写入外部系统状态
- 执行业务动作
- 对接平台已有开放接口

### 7.3 插件与MCP的区别

插件与 MCP 都属于外部能力接入，但侧重点不同。

插件更偏向：

- 明确的 HTTP 接口
- 平台内预先定义好工具协议

MCP 更偏向：

- 按 MCP 协议对接外部工具服务
- 由外部服务自行暴露 tool 定义

可理解为：

```text
插件
  -> 平台定义如何调用外部 API

MCP
  -> 外部 MCP 服务定义自己有哪些工具
```

## 8. MCP功能

### 8.1 功能定位

MCP 功能用于把符合 MCP 协议的外部工具服务接入 `BasicAgent`。

它解决的是：

- 智能体如何统一接入外部工具服务
- 如何让工具定义由工具服务自身声明
- 如何在标准协议下扩展能力

### 8.2 MCP与插件的边界

MCP 与插件都可以让 `BasicAgent` 调用外部能力，但两者侧重点不同：

- 插件偏 API 集成
- MCP 偏工具协议集成

插件更像：

- 已知接口的封装接入

MCP 更像：

- 标准工具协议下的能力发现与调用

## 9. 组件功能

### 9.1 功能定位

组件功能用于把平台内部已有应用能力复用给 `BasicAgent`。

它解决的是：

- 一个 agent 能否调用另一个已发布 agent
- 一个 agent 能否调用已发布 workflow
- 平台内已有能力如何复用而不重复建设

### 9.2 组件的两类功能

组件主要分为两类：

- agent 组件
- workflow 组件

功能区别是：

- agent 组件复用另一个智能体能力
- workflow 组件复用一个工作流能力

### 9.3 组件与插件/MCP的区别

插件和 MCP 面向的是外部能力接入。

组件面向的是内部能力复用。

可理解为：

```text
插件 / MCP
  -> 把外部能力接进来

组件
  -> 把内部能力重新暴露出来
```

## 10. SKILL功能

### 10.1 功能定位

SKILL 功能用于把一组可复用的专业知识、执行规范、提示词模板和操作方法装载到 `BasicAgent`。

它解决的是：

- 智能体如何具备某一领域的稳定做事方法
- 智能体如何在特定任务下遵循固定的分析与执行套路
- 智能体如何复用已经沉淀好的专业能力，而不是每次都重新编写 prompt

因此 SKILL 本质上是：

```text
可装载的专业能力包
```

### 10.2 SKILL的能力边界

SKILL 的核心不是直接提供外部工具调用，也不是替代模型本身。

它更适合承载：

- 某类任务的处理规范
- 某个领域的术语、规则和知识摘要
- 某种固定工作流的步骤说明
- 某类输出结果的结构约束

它不主要承担：

- 直接访问外部 API
- 直接执行数据库查询
- 替代 MCP、插件、组件这类外部执行能力

因此可以理解为：

```text
SKILL
  -> 负责“怎么做更专业”

插件 / MCP / 组件
  -> 负责“能去做什么动作”
```

### 10.3 SKILL与模板的区别

模板主要解决的是：

- 当前智能体整体应该如何说话
- 应该遵循什么角色和规则

SKILL 主要解决的是：

- 面对某类具体任务时，应采用什么专业方法
- 在特定场景下，应该参考哪套处理经验或规则

可理解为：

```text
模板
  -> 定义智能体的总体角色与行为边界

SKILL
  -> 提供面向具体任务的专业能力补充
```

### 10.4 SKILL与知识库的区别

知识库更偏向：

- 提供外部资料
- 提供事实文档
- 提供可检索的内容依据

SKILL 更偏向：

- 提供做事方法
- 提供规则、经验与范式
- 提供面向任务的能力封装

可理解为：

```text
知识库
  -> 我可以查到什么资料

SKILL
  -> 我应该如何处理这类任务
```

### 10.5 SKILL与插件/MCP/组件的区别

SKILL 与插件、MCP、组件都属于“增强智能体能力”的方式，但职责不同。

插件和 MCP 更偏向外部能力接入：

- 插件：封装 HTTP/OpenAPI 能力
- MCP：通过 MCP 协议接入工具服务

组件更偏向内部能力复用：

- 复用平台中已经发布的 agent 或 workflow

SKILL 更偏向能力知识注入：

- 不一定直接执行动作
- 更强调方法、规则、步骤和专业上下文

因此：

```text
插件 / MCP / 组件
  -> 扩展智能体“能执行什么”

SKILL
  -> 扩展智能体“应该怎样更专业地执行”
```

### 10.6 SKILL的功能价值

从功能设计上，SKILL 的主要价值包括：

- 让智能体具备领域化处理能力
- 让智能体在复杂任务中输出更稳定
- 让专业知识和处理套路能够被复用
- 降低大量 prompt 重复维护成本
- 提高不同智能体之间能力复用的一致性

### 10.7 SKILL的典型适用场景

SKILL 适合承担的典型场景包括：

- 行业术语解释与规范化表达
- 某类分析任务的固定步骤约束
- 报告生成、总结提炼、评估判断的标准方法
- 某类数据问答的专用解释规则
- 某类业务流程中的注意事项与输出模板

### 10.8 SKILL在BasicAgent中的协同位置

在 `BasicAgent` 中，SKILL 更适合作为“上下文增强能力”的一部分参与协同。

其典型作用路径是：

```text
用户问题
  -> 模板定义总体角色
  -> 模板变量注入本次上下文
  -> 记忆补充会话历史
  -> 知识库补充事实资料
  -> SKILL补充任务处理方法和专业规则
  -> 模型综合判断
  -> 必要时调用插件 / MCP / 组件执行动作
  -> 返回结果
```

因此 SKILL 更接近：

```text
面向任务方法论的上下文增强层
```

## 11. 各类能力的协同关系

### 10.1 核心协同方式

从功能设计上看，`BasicAgent` 的能力协同关系可以概括为：

```text
模型
  -> 负责理解、推理、决策与生成

模板与模板变量
  -> 负责规定行为边界和动态提示词

记忆
  -> 负责延续会话上下文

知识库
  -> 负责补充事实与文档上下文

SKILL
  -> 负责补充专业规则、处理方法与任务范式

插件 / MCP / 组件
  -> 负责提供外部或内部行动能力
```

### 11.2 信息流与行动流

从功能视角可以把它们分成两条链：

```text
信息流
  -> 模板
  -> 模板变量
  -> 记忆
  -> 知识库
  -> SKILL
  -> 共同影响模型“看到什么”

行动流
  -> 插件
  -> MCP
  -> 组件
  -> 共同影响模型“能做什么”
```

因此：

- 上下文类能力决定模型输入环境
- 工具类能力决定模型执行边界

### 11.3 典型协同场景

一个典型的 `BasicAgent` 功能协同场景可以是：

1. 用模板定义角色和规则
2. 用模板变量注入本次业务上下文
3. 用记忆保留会话历史
4. 用知识库补充领域资料
5. 用 SKILL 补充任务方法和专业规则
6. 由模型决定是否调用插件、MCP 或组件
7. 返回结果并继续延续对话

## 12. BasicAgent适合的功能场景

从整体功能设计看，`BasicAgent` 适合的场景包括：

- 通用问答型智能体
- 带业务规则的对话型智能体
- 需要调用外部系统的执行型智能体
- 基于企业知识库的咨询型智能体
- 需要领域方法论沉淀的专业型智能体
- 需要多能力复用的组合型智能体

尤其适合：

- 模型 + 知识库 + 工具
- 模型 + 记忆 + 模板变量
- 模型 + SKILL + 知识库
- 模型 + 内部组件复用

这类复合型智能体场景。

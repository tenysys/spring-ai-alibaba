# 意图识别智能体设计方案

## 1. 目标

当前已有两类专用智能体：

- 问数智能体：定义于 `app/src/main/java/com/nrec/service/app/config/DataAgentConfig.java` 的 `nl2sqlGraph`
- 问答智能体：定义于 `agent-designer/src/main/java/com/nrec/service/basicagent/executor/BasicAgentExecutor.java` 的 `streamExecute`

本方案目标：

- 新增一个主智能体，负责意图识别与路由分发
- 主智能体根据用户问题在多个专用智能体之间选择最合适的执行目标
- 最终对外输出格式保持为 `Flux<AgentResponse>`
- 子智能体输出作为最终展示内容，保持流式返回
- 后续可继续扩展更多专用智能体，不需要重做整体架构

## 2. 设计结论

不建议把整个执行链强制收敛成纯 graph-native 子图编排。

更适合当前系统的方式是：

- 使用 Routing Graph 做控制面，只负责意图识别和路由决策
- 使用 Adapter 做数据面，只负责调用具体专用智能体并透传其 `Flux<AgentResponse>`
- 主智能体最终直接返回命中的子智能体流，不做二次总结、不做格式重编码

推荐架构如下：

```text
RouterAgentExecutionService
  -> IntentRoutingGraph
       -> PreprocessNode
       -> IntentClassifyNode
       -> DecisionNormalizeNode
  -> SpecializedAgentRegistry
       -> DataAgentAdapter
       -> QaAgentAdapter
       -> Future adapters...
  -> return Flux<AgentResponse>
```

## 3. 采用该方案的原因

### 3.1 满足最终输出要求

当前系统最终统一输出契约已经是 `Flux<AgentResponse>`：

- 问数流式执行入口：`GraphService.graphStreamProcess(...)`
- 问答流式执行入口：`AgentExecutionService.streamCall(...)`

如果把问答智能体先适配成 `Flux<NodeOutput>` 或 `Flux<StreamingOutput>`，最终仍然要再转换回 `Flux<AgentResponse>`，改造成本高，且没有明显收益。

### 3.2 复用现有成熟能力

问数智能体当前已经具备：

- Graph 编排
- 中断恢复
- SSE 输出
- `AgentResponse` 转换
- 文本类型识别

问答智能体当前已经具备：

- 运行时上下文解析
- 多轮上下文管理
- 知识召回
- 流式输出
- `AgentResponse` 统一封装

因此最稳妥的做法不是重写它们，而是通过统一适配层复用。

### 3.3 方便扩展更多专用智能体

如果主智能体未来还要接：

- 报告智能体
- 工作流智能体
- 搜索智能体
- MCP 工具型智能体

只要新增：

- 一个新的 `AgentAppType` 或复用已有 `AgentAppType`
- 一个新的 `SpecializedAgentAdapter`
- 在路由智能体 runtime config 中增加子智能体描述
- 补充每个子智能体的功能说明和路由条件

即可完成扩展。

## 4. 总体架构

### 4.1 控制面

控制面只负责：

- 预处理用户输入
- 判断意图属于哪个路由目标
- 输出标准化决策结果

建议使用一个轻量 Routing Graph 完成。

### 4.2 数据面

数据面只负责：

- 根据路由目标找到对应专用智能体
- 构造该专用智能体所需请求对象
- 调用原有流式服务
- 直接透传 `Flux<AgentResponse>`

### 4.3 输出面

输出面仍沿用当前控制器统一的 `dealStream(...)` 聚合逻辑，保持外部 API 不变。

## 5. 核心抽象设计

### 5.1 路由目标类型

不再新增 `RouteTarget`。

路由目标类型直接复用当前项目已有的 `AgentAppType`：

```java
public enum AgentAppType {
    BASIC,
    DATA,
    REPORT,
    QUESTION,
    WORKFLOW,
    ADVANCED_CHAT,
    NONE
}
```

说明：

- `AgentAppType` 已经是智能体应用的统一类型定义，位于 `agent-designer/src/main/java/com/nrec/service/basicagent/enums/AgentAppType.java`
- 路由智能体不应再引入一套重复的目标类型枚举
- 但 `AgentAppType` 只能表达“类型”，不能唯一表达“具体哪个智能体实例”
- 因此精确路由必须同时返回 `agentId` 和 `agentType`
- 例如两个问数智能体都属于 `AgentAppType.DATA`，仅返回 `DATA` 无法区分命中目标

### 5.2 路由结果对象

```java
@Data
@Builder
public class RouteDecision {

    private String targetAgentId;

    private AgentAppType targetAgentType;

    private Double confidence;

    private String reason;

    private Map<String, Object> attributes;
}
```

字段说明：

- `targetAgentId`：命中的子智能体 ID，用于精确路由
- `targetAgentType`：命中的子智能体类型，复用 `AgentAppType`
- `confidence`：LLM 对命中目标的置信度；如果系统因低置信度改写为兜底目标，该值仍保留原始 LLM 置信度
- `reason`：命中原因
- `attributes`：扩展属性，例如业务域、子智能体配置、原始模型输出

### 5.3 主智能体请求对象

建议单独定义 Router 请求对象，不直接复用 `GraphRequest` 或 `AgentRequest`：

```java
@Data
@Builder
public class RouterAgentRequest {

    private String routerAgentId;

    private String sessionId;

    private String threadId;

    private String question;

    private String userId;

    private Map<String, Object> extraParams;
}
```

### 5.4 专用智能体统一适配接口

```java
public interface SpecializedAgentAdapter {

    AgentAppType supportType();

    Flux<AgentResponse> streamExecute(RouterAgentRequest request, RoutedAgent routedAgent);
}
```

说明：

- 所有专用智能体最终统一对外暴露 `Flux<AgentResponse>`
- 主智能体不感知内部是 Graph、ChatClient 还是别的执行模型
- Adapter 按 `AgentAppType` 匹配，具体执行哪个智能体实例由 `RoutedAgent.agentId` 决定

建议新增一个内部路由目标对象：

```java
@Data
@Builder
public class RoutedAgent {

    private String agentId;

    private AgentAppType agentType;

    private String name;

    private String description;
}
```

### 5.5 Adapter Registry

```java
@Component
public class SpecializedAgentRegistry {

    private final Map<AgentAppType, SpecializedAgentAdapter> adapterMap;

    public SpecializedAgentRegistry(List<SpecializedAgentAdapter> adapters) {
        this.adapterMap = adapters.stream()
                .collect(Collectors.toMap(SpecializedAgentAdapter::supportType, a -> a));
    }

    public SpecializedAgentAdapter get(AgentAppType agentType) {
        SpecializedAgentAdapter adapter = adapterMap.get(agentType);
        if (adapter == null) {
            throw new ServiceException("No adapter for agentType: " + agentType);
        }
        return adapter;
    }
}
```

## 6. 两个现有专用智能体的接入方式

### 6.1 问数智能体接入

建议新增 `DataAgentAdapter`。

内部实现方式：

- 构造 `GraphRequest`
- 调用 `GraphService.graphStreamProcess(...)`
- 将 `Sinks.Many<ServerSentEvent<AgentResponse>>` 转成 `Flux<AgentResponse>`

示意代码：

```java
@Component
@RequiredArgsConstructor
public class DataAgentAdapter implements SpecializedAgentAdapter {

    private final GraphService graphService;
    private final RouterRuntimeConfigResolver runtimeConfigResolver;

    @Override
    public AgentAppType supportType() {
        return AgentAppType.DATA;
    }

    @Override
    public Flux<AgentResponse> streamExecute(RouterAgentRequest request, RoutedAgent routedAgent) {
        Sinks.Many<ServerSentEvent<AgentResponse>> sink =
                Sinks.many().unicast().onBackpressureBuffer();

        GraphRequest graphRequest = new GraphRequest();
        graphRequest.setAgentId(routedAgent.getAgentId());
        graphRequest.setSessionId(request.getSessionId());
        graphRequest.setThreadId(request.getThreadId());
        graphRequest.setQuery(request.getQuestion());

        graphService.graphStreamProcess(sink, graphRequest);

        return sink.asFlux().mapNotNull(ServerSentEvent::data);
    }
}
```

该方式的优点：

- 不破坏现有 `GraphServiceImpl` 的流式行为
- 不丢失问数智能体原有的中断、恢复、文本类型、节点名称等语义

### 6.2 问答智能体接入

建议新增 `QaAgentAdapter`。

内部实现方式：

- 构造 `AgentRequest`
- 调用 `AgentExecutionService.streamCall(...)`
- 将 `Sinks.Many<ServerSentEvent<AgentResponse>>` 转成 `Flux<AgentResponse>`

示意代码：

```java
@Component
@RequiredArgsConstructor
public class QaAgentAdapter implements SpecializedAgentAdapter {

    private final AgentExecutionService agentExecutionService;
    private final RouterRuntimeConfigResolver runtimeConfigResolver;

    @Override
    public AgentAppType supportType() {
        return AgentAppType.QUESTION;
    }

    @Override
    public Flux<AgentResponse> streamExecute(RouterAgentRequest request, RoutedAgent routedAgent) {
        Sinks.Many<ServerSentEvent<AgentResponse>> sink =
                Sinks.many().unicast().onBackpressureBuffer();

        AgentRequest agentRequest = new AgentRequest();
        agentRequest.setAgentId(routedAgent.getAgentId());
        agentRequest.setSessionId(request.getSessionId());
        agentRequest.setThreadId(request.getThreadId());
        agentRequest.setQuery(request.getQuestion());
        agentRequest.setStream(true);
        agentRequest.setExtraParams(request.getExtraParams());

        agentExecutionService.streamCall(agentRequest, sink);

        return sink.asFlux().mapNotNull(ServerSentEvent::data);
    }
}
```

该方式的优点：

- 不需要把 `BasicAgentExecutor.streamExecute(...)` 改造成 graph-native
- 不需要进行 `AgentResponse -> NodeOutput -> AgentResponse` 的重复转换

## 7. Intent Routing Graph 设计

### 7.1 角色定位

Routing Graph 只负责意图识别，不负责执行子智能体，不负责总结结果。

### 7.2 推荐节点

建议图中包含三个节点：

- `PreprocessNode`
- `IntentClassifyNode`
- `DecisionNormalizeNode`

### 7.3 节点职责

#### PreprocessNode

职责：

- 标准化用户问题
- 去除无效空白
- 限制过长输入
- 补充 traceId 和时间戳等元数据

输出：

- `normalized_question`
- `route_trace`

#### IntentClassifyNode

职责：

- 读取 runtime config 中的 `agents` 以及每个子智能体的 `capability`、`routeCondition`
- 调用模型从候选子智能体中选择一个最合适的具体 `agentId`
- 将模型输出解析为固定结构

输出：

- `route_agent_id`
- `route_agent_type`
- `route_confidence`
- `route_reason`

#### DecisionNormalizeNode

职责：

- 标准化分类结果
- 校验 LLM 输出结构和子智能体配置
- 根据用户配置的 `minConfidence` 判断是否改写为 `fallbackTarget`
- 统一输出 `RouteDecision`

输出：

- `route_decision`

处理规则：

1. JSON 解析失败：返回路由错误，不走兜底
2. `agentId` 不存在于 runtime config 的 `agents`：返回路由错误，不走兜底
3. `agentType` 与 `agentId` 对应配置不一致：返回路由错误，不走兜底
4. `confidence` 低于用户配置的 `minConfidence`：将最终 `targetAgentId` 和 `targetAgentType` 改写为 `fallbackTarget`
5. 其他情况：使用 LLM 返回的 `agentId` 和 `agentType`

说明：

- 是否低置信度完全由用户配置的 `minConfidence` 阈值决定，不由模型决定
- `RouteDecision` 不包含 `fallback`、`fallbackReason`
- 如果需要审计低置信度改写，可把原始 LLM 输出和命中阈值写入 `attributes` 或日志，不作为主决策字段

## 8. 分类策略

### 8.1 推荐策略

采用“先配置候选子智能体，再为每个子智能体配置路由说明，系统生成最终 prompt”的策略。

说明：

- 平台只约束 LLM 最终返回的 JSON 结构
- 路由配置顺序是先配置支持路由的子智能体，再配置每个子智能体的功能说明和路由条件
- 用户不直接编辑完整 prompt，只填写每个子智能体“做什么”和“什么情况下路由到它”
- 系统根据固定开头、子智能体元信息、用户填写的功能说明和路由条件生成最终 prompt
- 系统在调用分类模型前，将候选子智能体列表拼入 prompt，避免 LLM 返回不存在的 agentId

### 8.2 配置顺序

推荐前端配置顺序：

1. 选择支持路由的子智能体
2. 展示每个子智能体的固定元信息：`agentId`、`agentType`、`name`、`description`
3. 在每个子智能体后方提供输入框，由用户填写：
   - 子智能体功能补充说明
   - 什么情况下应该路由到该子智能体
4. 配置 `minConfidence` 和 `fallbackTarget`
5. 展示系统生成的最终 prompt 预览

### 8.3 最终 Prompt 拼装规则

最终 prompt 由系统拼装，不建议用户直接整体编辑。

固定开头：

```text
你是一个智能体路由器，需要根据用户问题选择最合适的一个子智能体。

你只能从候选子智能体列表中选择一个 agentId。
如果多个候选子智能体类型相同，必须根据每个子智能体的 name、description、功能说明和路由条件选择最匹配的具体 agentId。
如果无法判断，选择 fallbackTarget 指定的智能体。

候选子智能体如下：
{{agent_catalog}}

用户问题：
{{question}}

请严格返回 JSON，不要输出 Markdown，不要输出额外解释。
```

其中 `{{agent_catalog}}` 由系统根据 runtime config 自动渲染。每个子智能体都会拼接：

- `agentId`
- `agentType`
- `name`
- `description`
- 用户填写的 `capability`
- 用户填写的 `routeCondition`

示例：

```text
- agentId: sales-data-agent
  agentType: data
  name: 销售问数智能体
  description: 负责销售额、订单、客户、区域业绩等数据查询
  capability: 查询销售额、订单、客户和区域业绩相关指标
  routeCondition: 当用户询问销售统计、销售趋势、客户订单、区域排行时路由到该智能体
- agentId: inventory-data-agent
  agentType: data
  name: 库存问数智能体
  description: 负责库存、仓储、缺货、周转等数据查询
  capability: 查询库存、仓储、缺货和周转相关指标
  routeCondition: 当用户询问库存余量、缺货风险、仓储周转时路由到该智能体
- agentId: qa-agent
  agentType: question
  name: 知识库问答智能体
  description: 负责制度、流程、操作说明、知识库文档问答
  capability: 回答制度、流程、操作说明和知识库文档问题
  routeCondition: 当用户询问概念解释、操作流程、制度说明、文档内容时路由到该智能体
```

### 8.4 DATA 场景关键词

以下语义优先路由到问数智能体：

- 指标
- 维度
- 统计
- 汇总
- SQL
- 查询某表
- 趋势
- 同比
- 环比
- TopN
- 排名
- 图表
- 数据分布
- 报表数据

这些关键词不再写死为唯一分类策略，只作为默认 prompt 示例或后台辅助提示。

### 8.5 QA 场景关键词

以下语义优先路由到问答智能体：

- 是什么
- 为什么
- 怎么做
- 解释
- 说明
- 文档
- 知识库
- 概念
- 流程
- 规则说明

这些关键词不再写死为唯一分类策略，只作为默认 prompt 示例或后台辅助提示。

### 8.6 LLM 输出格式

建议严格输出固定 JSON：

```json
{
  "agentId": "sales-data-agent",
  "agentType": "data",
  "confidence": 0.92,
  "reason": "..."
}
```

字段说明：

- `agentId`：命中的具体子智能体 ID，必须来自 runtime config 的 `agents` 列表
- `agentType`：命中的智能体类型，使用 `AgentAppType.code`，例如 `data`、`question`、`report`
- `confidence`：置信度
- `reason`：路由原因

注意：

- LLM 不输出 `fallback`
- 是否使用 `fallbackTarget` 是系统在决策标准化阶段根据用户配置的 `minConfidence` 阈值判断的结果
- LLM 只负责选择它认为最合适的 `agentId`

这样即使路由智能体下挂多个同类型子智能体，例如两个 `data` 智能体，也可以通过 `agentId` 做精确路由。

### 8.7 fallback 策略

建议配置默认兜底目标，例如：

- 默认兜底到某个具体 `agentId`

fallback 只处理低置信度场景。

不走 fallback 的错误场景：

- LLM 输出不是合法 JSON
- LLM 输出缺少 `agentId`、`agentType`、`confidence` 等必要字段
- LLM 返回的 `agentId` 不在 runtime config 的 `agents` 列表中
- LLM 返回的 `agentType` 与该 `agentId` 的配置类型不一致

这些场景属于输出协议错误或配置错误，应通过流式错误事件返回前端，方便用户修正 prompt 或子智能体配置。

## 9. 主执行服务设计

建议新增 `RouterAgentExecutionService`。

职责：

- 接收 Router 请求
- 调用 Routing Graph 得到路由结果
- 根据 `RouteDecision.targetAgentType` 从 Registry 中获取 Adapter
- 根据 `RouteDecision.targetAgentId` 定位具体子智能体
- 返回命中的 `Flux<AgentResponse>`

示意代码：

```java
@Service
@RequiredArgsConstructor
public class RouterAgentExecutionService {

    private final IntentRoutingService intentRoutingService;
    private final SpecializedAgentRegistry registry;
    private final RouterRuntimeConfigResolver runtimeConfigResolver;

    public Flux<AgentResponse> streamCall(RouterAgentRequest request) {
        return Mono.fromCallable(() -> intentRoutingService.route(request))
                .flatMapMany(decision -> {
                    RoutedAgent routedAgent = runtimeConfigResolver.resolveRoutedAgent(
                            request.getRouterAgentId(), decision.getTargetAgentId());
                    SpecializedAgentAdapter adapter = registry.get(decision.getTargetAgentType());
                    return adapter.streamExecute(request, routedAgent);
                });
    }
}
```

路由阶段异常不能只抛给调用栈，也不能静默走兜底。由于外部接口是 SSE 流式输出，路由错误需要转换为 `Flux<AgentResponse>` 中的错误响应，再由 `agent-api` 现有 `dealStream(...)` 统一转换为前端错误事件。

建议增加路由错误响应构造：

```java
public Flux<AgentResponse> streamCall(RouterAgentRequest request) {
    return Mono.fromCallable(() -> intentRoutingService.route(request))
            .flatMapMany(decision -> {
                RoutedAgent routedAgent = runtimeConfigResolver.resolveRoutedAgent(
                        request.getRouterAgentId(), decision.getTargetAgentId());
                SpecializedAgentAdapter adapter = registry.get(decision.getTargetAgentType());
                return adapter.streamExecute(request, routedAgent);
            })
            .onErrorResume(RouteException.class, ex -> Flux.just(buildRouteErrorResponse(request, ex)));
}

private AgentResponse buildRouteErrorResponse(RouterAgentRequest request, RouteException ex) {
    return AgentResponse.builder()
            .threadId(request.getThreadId())
            .nodeName("IntentRoutingNode")
            .text(ex.getMessage())
            .textType(TextType.TEXT)
            .status(AgentStatus.FAILED)
            .build();
}
```

建议定义明确的路由错误码：

```java
public enum RouteErrorCode {
    ROUTE_OUTPUT_PARSE_ERROR,
    ROUTE_OUTPUT_MISSING_FIELD,
    ROUTE_UNKNOWN_AGENT_ID,
    ROUTE_AGENT_TYPE_MISMATCH
}
```

错误处理原则：

- `ROUTE_OUTPUT_PARSE_ERROR`：模型输出无法解析为 JSON，返回错误事件
- `ROUTE_OUTPUT_MISSING_FIELD`：缺少必要字段，返回错误事件
- `ROUTE_UNKNOWN_AGENT_ID`：返回了未配置的 `agentId`，返回错误事件
- `ROUTE_AGENT_TYPE_MISMATCH`：`agentType` 与配置不一致，返回错误事件
- 低置信度不是错误，系统根据 `minConfidence` 使用 `fallbackTarget` 生成正常 `RouteDecision`

如果需要把路由过程暴露给前端，可选地在子流前插入一条事件：

```java
Flux<AgentResponse> routeEvent = Flux.just(
        AgentResponse.builder()
                .threadId(request.getThreadId())
                .nodeName("IntentRoutingNode")
                .text("route=" + decision.getTargetAgentId())
                .textType(TextType.TEXT)
                .build()
);

return routeEvent.concatWith(adapter.streamExecute(request));
```

如果要求“最终展示只保留子智能体输出”，则不发送该事件。

## 10. 控制器接入方式

当前统一流式出口在：

- `data-agent-service/agent-api/src/main/java/com/nrec/service/api/controller/AgentStreamController.java`

核心执行逻辑放在：

- `data-agent-service/router-agent`

建议改造如下：

### 10.1 扩展 AgentAppType

在 `AgentAppType` 中新增：

```java
ROUTER("router")
```

说明：

- 这里的 `ROUTER` 表示“路由智能体自身”的应用类型
- 路由结果中的目标类型仍复用 `AgentAppType`，例如 `DATA`、`QUESTION`、`REPORT`
- 不新增 `RouteTarget`

### 10.2 扩展 dispatchStream

在 `dispatchStream(...)` 中新增：

```java
case ROUTER -> streamRouterAgent(...);
```

### 10.3 新增 streamRouterAgent

其实现方式与现有 `streamBasicAgent(...)` / `streamDataAgent(...)` 一致：

- 构造 `RouterAgentRequest`
- 调用 `RouterAgentExecutionService.streamCall(...)`
- 将 `Flux<AgentResponse>` 转换成 `Sinks.Many<ServerSentEvent<AgentResponse>>`
- 复用现有 `dealStream(...)`

实现边界：

- `agent-api` 只负责外部 HTTP/SSE 接入、鉴权、会话、消息聚合和落库
- `agent-api` 不承载路由分类、runtime config 解析、Adapter Registry 等核心逻辑
- `router-agent` 提供 `RouterAgentExecutionService` 等内部服务，供 `agent-api` 注入调用

这样可最大程度复用现有：

- SSE 输出
- 消息聚合
- 落库
- usage 统计
- complete / error 处理

## 11. Runtime Config 设计

因为该主智能体未来会继续路由更多专用智能体，建议其自身具备独立 runtime config。

推荐结构：

```json
{
  "agents": [
    {
      "agentId": "sales-data-agent",
      "agentType": "data",
      "name": "销售问数智能体",
      "description": "负责销售额、订单、客户、区域业绩等数据查询",
      "capability": "查询销售额、订单、客户和区域业绩相关指标",
      "routeCondition": "当用户询问销售统计、销售趋势、客户订单、区域排行时路由到该智能体"
    },
    {
      "agentId": "inventory-data-agent",
      "agentType": "data",
      "name": "库存问数智能体",
      "description": "负责库存、仓储、缺货、周转等数据查询",
      "capability": "查询库存、仓储、缺货和周转相关指标",
      "routeCondition": "当用户询问库存余量、缺货风险、仓储周转时路由到该智能体"
    },
    {
      "agentId": "qa-agent",
      "agentType": "question",
      "name": "知识库问答智能体",
      "description": "负责制度、流程、操作说明、知识库文档问答",
      "capability": "回答制度、流程、操作说明和知识库文档问题",
      "routeCondition": "当用户询问概念解释、操作流程、制度说明、文档内容时路由到该智能体"
    }
  ],
  "emitRouteEvent": false,
  "minConfidence": 0.6,
  "fallbackTarget": {
    "agentId": "qa-agent",
    "agentType": "question"
  }
}
```

字段说明：

- `agents`：路由智能体可选择的子智能体集合
- `agents[].agentId`：具体子智能体 ID
- `agents[].agentType`：子智能体类型，使用 `AgentAppType.code`
- `agents[].name`：子智能体展示名称，来自智能体元信息
- `agents[].description`：子智能体说明，来自智能体元信息
- `agents[].capability`：用户填写的子智能体功能补充说明
- `agents[].routeCondition`：用户填写的路由条件，说明什么情况下路由到该子智能体
- `emitRouteEvent`：是否向前端输出路由事件
- `minConfidence`：最低置信度阈值，低于该值时才使用 `fallbackTarget`
- `fallbackTarget`：默认兜底目标，必须指向具体 `agentId` 和 `agentType`

不再保留：

- `routeMode`
- `classifierModel`

原因：

- 路由模式当前先统一按“子智能体路由配置 + 系统生成 prompt + 结构化输出 + fallback”实现，避免过早暴露无效配置
- 分类模型应复用路由智能体自身模型配置或后续统一模型配置机制，不在 runtime config 中单独固定

后续扩展更多专用智能体时，只需要向 `agents` 增加元素，不需要增加新的固定字段。

## 12. 推荐包结构

建议按模块功能单一原则拆分：

- `router-agent`：只负责意图识别、路由决策、Adapter Registry、子智能体调用适配

- `agent-designer`：保持智能体设计、模板、应用管理等原有职责，不承载路由智能体核心逻辑

## 13. 实施步骤

### 第一阶段：可用版本

目标：

- 快速上线一个可路由、可流式输出的主智能体

步骤：

1. 新增 `ROUTER` 类型
2. 新增 `router-agent` 模块
3. 在 `router-agent` 中新增 `RouteDecision`、`RouterAgentRequest`、`RoutedAgent`、`RouterRuntimeConfig`
4. 在 `router-agent` 中新增 `SpecializedAgentAdapter`、`DataAgentAdapter`、`QaAgentAdapter`
5. 在 `router-agent` 中新增 `SpecializedAgentRegistry`
6. 在 `router-agent` 中新增基于子智能体路由配置的 `IntentRoutingService`
7. 在 `router-agent` 中新增 `RouterAgentExecutionService`
8. 在 `AgentStreamController` 中增加 `streamRouterAgent(...)`，调用 `router-agent` 暴露的执行服务

该阶段可不引入完整 graph，只要先把路由跑通。

第一阶段要保证：

- 子智能体集合来自 runtime config 的 `agents`
- LLM 输出固定解析为 `agentId + agentType + confidence + reason`
- 如果 LLM 返回不存在的 `agentId`，通过流式错误事件返回前端
- 如果 `agentType` 与配置中的子智能体类型不一致，通过流式错误事件返回前端
- 如果 `confidence` 低于 `minConfidence`，走 `fallbackTarget`

### 第二阶段：引入 Intent Routing Graph

目标：

- 将主智能体的意图识别过程收敛为可维护的 graph 结构

步骤：

1. 新增 `IntentRoutingGraphFactory`
2. 增加 `PreprocessNode`
3. 增加 `IntentClassifyNode`
4. 增加 `DecisionNormalizeNode`
5. 将 `IntentRoutingService` 改为委托 Routing Graph 执行

### 第三阶段：增强扩展能力

目标：

- 支持更多专用智能体
- 支持复杂路由与 fallback 策略

步骤：

1. 复用或增加新的 `AgentAppType`
2. 新增对应 `SpecializedAgentAdapter`
3. 向 runtime config 的 `agents` 增加子智能体配置
4. 增加低置信度 fallback 规则
5. 增加路由评估与命中统计

### 14.1 支持更多专用智能体

## 15. 不建议采用的方案

### 15.1 不建议使用 Supervisor + Tool

原因：

- 子智能体流式输出无法直接透传
- 当前 `AgentTool` 模式更适合“工具式委托 + 返回最终结果”
- 不适合“子智能体输出即最终展示”的场景

### 15.2 不建议强制把问答智能体改造成 graph-native 子图

原因：

- 当前问答链路已经稳定
- 改造量大
- 最终输出契约仍然是 `Flux<AgentResponse>`
- 需要额外做 `AgentResponse -> NodeOutput -> AgentResponse` 往返转换

### 15.3 不建议主智能体二次总结

原因：

- 会破坏“子智能体输出即最终展示”
- 会增加延迟
- 会引入二次 hallucination 风险

## 16. 最终建议

本项目中，意图识别智能体应采用如下方案：

- 主智能体负责意图识别与路由，不负责内容总结
- 采用 Routing Graph 组织意图识别流程
- 采用 Adapter 统一接入不同专用智能体
- 专用智能体统一暴露 `Flux<AgentResponse>`
- 主智能体最终直接返回命中的子智能体流

一句话总结：

**用 Routing Graph 做控制面，用 Adapter Registry 做数据面，最终保持 `Flux<AgentResponse>` 直通输出。**

# SophicAgent 数据库结构设计（NRSql 版）

## 1. 文档说明

本文基于以下 MySQL 版文档转换形成 NRSql 版数据库结构设计：

- `.claude/sophicAgent/sophicAgent数据库设计_V1_V2.md`
- `.claude/sophicAgent/数据库表明细.md`
- `.claude/sophicAgent/数据库结构设计.md`

设计目标是在不改变 SophicAgent 业务模型、关系模型和分域边界的前提下，将原有 MySQL 版设计迁移为一份适用于 NRSql 的结构设计文档。由于 NRSql 的语法和数据类型与 PostgreSQL 一致，因此本文按 PostgreSQL 方言组织物理设计，覆盖：

- 概念结构保持不变
- 逻辑结构保持不变
- 物理结构按 NRSql 方言重写
- 给出 MySQL 到 NRSql 的类型与语法映射规范

本文默认采用以下迁移前提：

- NRSql 与 PostgreSQL 在 DDL、约束、索引、注释、identity、sequence、`json/jsonb`、时间类型等方面保持一致。
- NRSql 不依赖 MySQL 的 `ENGINE=InnoDB`、`DEFAULT CHARSET=utf8mb4`、`AUTO_INCREMENT`、`ON UPDATE CURRENT_TIMESTAMP` 等专有语法。
- 非结构化配置字段优先使用 `jsonb`，仅在极大文本或纯展示大对象场景下使用 `text`。
- 对高并发运行事实表，优先保持“业务外键 + 索引”的轻约束策略，不强制所有运行表都落强外键。

因此，NRSql 版设计可直接采用 PostgreSQL 风格的建表、索引、注释和时间字段策略，不再保留通用数据库兼容层假设。

## 2. 设计原则

- 新增 SophicAgent 表统一保留物理主键 `id`，类型采用 `bigint`。
- MySQL 中的 `unsigned bigint auto_increment` 统一转换为 NRSql 的 `bigint generated by default as identity`，必要时可退回 `sequence + default nextval(...)` 方案。
- 主业务实体仍采用 `xxx_id` 作为业务主键，必要时补充 `xxx_code` 作为业务编码。
- 业务层表关联优先使用业务标识，不直接对外暴露物理主键 `id`。
- 纯关系表、中间表、统计事实表不强制增加业务 UUID，继续通过组合唯一约束或组合索引表达业务唯一性。
- 既有存量表继续沿用现有结构，不因迁移 NRSql 而强制统一其历史主键类型。
- 状态字段继续采用 `status`，启停控制字段继续采用 `enabled`。
- 时间字段继续采用 `gmt_create`、`gmt_modified`，运行态补充 `gmt_start`、`gmt_end`、`gmt_last_active`。
- 配置快照、DSL、规则、元数据等非结构化内容统一优先采用 NRSql 原生 `jsonb`。
- 资源授权仍统一通过 `sa_resource` + `sa_resource_acl` 建模。
- 标签能力仍统一通过 `sa_tag` + `sa_tag_binding` 建模。
- 工作流 V1 仍采用“版本快照存储”模式，工作流节点、边、画布统一存入 `sa_application_version.config_snapshot`。

## 3. MySQL 到 NRSql 映射规范（PostgreSQL 等价）

### 3.1 主键与自增策略

MySQL 版：

```sql
id bigint unsigned not null auto_increment primary key
```

NRSql 标准写法：

```sql
id bigint generated by default as identity primary key
```

约定：

- 优先使用 identity。
- 若个别场景需要与历史 sequence 机制兼容，可使用 `sequence + default nextval(...)`。
- 不再使用 `unsigned`，统一以 `bigint` 承载正向增长主键。

### 3.2 字段类型映射

| MySQL 类型 | NRSql 建议类型 | 说明 |
|---|---|---|
| `bigint unsigned` | `bigint` | NRSql 版取消 unsigned |
| `int` | `integer` | 常规整型 |
| `tinyint` | `smallint` | 状态、布尔、枚举值 |
| `decimal(p,s)` | `decimal(p,s)` | 保持不变 |
| `varchar(n)` | `varchar(n)` | 保持不变 |
| `text` | `text` | PostgreSQL 等价文本类型 |
| `longtext` | `text` | NRSql 按 PostgreSQL 语义统一为 `text` |
| `datetime` | `timestamp` | 推荐统一为 `timestamp` |
| `date` | `date` | 保持不变 |
| `json` | `jsonb` | 优先使用 `jsonb` |

补充约定：

- `status`、`enabled` 建议使用 `smallint`，取值语义由应用枚举控制。
- 原 MySQL 中的 `decimal(1)`、`tinyint(1)` 不再表达“布尔字段语义”，统一按 `smallint` 建模。
- `content`、`summary_content`、`question`、`generated_answer` 等长文本字段统一使用 `text`。
- `config_snapshot`、`metadata`、`rule_snapshot`、`dsl_schema` 等结构化快照字段优先使用 `jsonb`。

### 3.3 默认值与时间更新策略

MySQL 常见写法：

```sql
gmt_create datetime not null default current_timestamp,
gmt_modified datetime not null default current_timestamp on update current_timestamp
```

NRSql 迁移约定：

- `gmt_create`：使用 `default current_timestamp`
- `gmt_modified`：使用 `default current_timestamp`
- 自动更新时间不依赖列级 `on update` 语法
- `gmt_modified` 更新由以下任一方式保证：
  - 应用层统一写入
  - ORM 自动填充
  - 数据库触发器更新

推荐：

- 主数据表可使用触发器维护 `gmt_modified`
- 高频写入运行表建议由应用层维护，减少触发器开销

### 3.4 注释、字符集与存储引擎

MySQL 中以下语法不再使用：

- `ENGINE=InnoDB`
- `DEFAULT CHARSET=utf8mb4`
- 列尾 `COMMENT 'xxx'`

NRSql 迁移建议：

- 字符集和编码按数据库实例统一配置，不在单表 DDL 中声明
- 表注释和列注释使用 `comment on table` / `comment on column`
- 存储引擎概念沿用 PostgreSQL 语义，不在 DDL 中声明

示例：

```sql
comment on table sa_application is '应用主表';
comment on column sa_application.agent_id is '应用业务主键';
```

### 3.5 索引与约束迁移

MySQL 中：

- `unique key uk_xxx (...)`
- `key idx_xxx (...)`

NRSql 中建议：

- `constraint uk_xxx unique (...)`
- `create index idx_xxx on table_name (...)`

约定：

- 主键、唯一约束在 `create table` 中声明
- 普通索引在 `create index` 中单独声明
- 运行态大表索引数量继续控制在 `3~5` 组核心索引以内

## 4. 概念结构设计

SophicAgent 的概念结构在 NRSql 版中保持不变，仍划分为五个概念域：

1. 账号权限域
2. 应用与设计器域
3. 运行时域
4. 能力资产域
5. 治理观测与运营域

核心实体、业务边界和域间关系与 MySQL 版保持一致，不因数据库方言变化而调整业务模型。

## 5. 逻辑结构设计

### 5.1 逻辑分层

| 逻辑层 | 说明 | 代表表 |
|---|---|---|
| 基础身份层 | 用户、组织、角色、权限、菜单 | `users`、`priv_group`、`priv_role`、`priv_permission` |
| 统一资源层 | 对业务对象进行统一注册与授权 | `sa_resource`、`sa_resource_acl` |
| 设计态定义层 | 模板、应用、版本、绑定、规则 | `sa_agent_template`、`sa_application`、`sa_application_version`、`sa_application_binding` |
| 运行态执行层 | 会话、消息、任务、执行步骤、运行日志 | `sa_session`、`sa_session_message`、`sa_task`、`sa_execution_step` |
| 能力资产层 | 知识、工具、MCP、记忆、数据源 | `sa_knowledge_base`、`sa_tool`、`sa_mcp_server`、`sa_memory_library`、`sa_datasource` |
| 治理运营层 | 模型、发布、反馈、评测、压测、指标 | `sa_model_provider`、`sa_publish_record`、`sa_eval_task`、`sa_runtime_metric` |

### 5.2 逻辑关系保持不变

以下关系保持与 MySQL 版一致：

- `users` 通过 `priv_user_group_relation` 与 `priv_group` 建立多对多关系
- `priv_group` 通过 `priv_group_role_relation` 与 `priv_role` 建立多对多关系
- `priv_role` 通过 `priv_role_permission_relation` 与 `priv_permission` 建立多对多关系
- `sa_application` 与 `sa_application_version` 构成主从版本结构
- `sa_application` 与 `sa_application_binding`、`sa_guardrail_rule` 构成设计态附属关系
- `sa_session`、`sa_session_message`、`sa_task`、`sa_execution_step` 构成运行态执行链路
- `sa_knowledge_base`、`sa_knowledge_document`、`sa_knowledge_chunk` 构成知识三层结构
- `sa_tool`、`sa_tool_version`、`sa_tool_debug_record` 构成工具三层结构
- `sa_mcp_server`、`sa_mcp_server_instance` 构成 MCP 服务结构
- `sa_memory_library`、`sa_memory_rule`、`sa_memory_long_term`、`sa_memory_hit_record`、`sa_memory_entity`、`sa_memory_recall_test` 构成记忆体系
- `sa_datasource`、`sa_datasource_table`、`sa_datasource_field`、`sa_datasource_relation`、`sa_datasource_semantic_model` 构成结构化数据资产体系
- `sa_model_provider`、`sa_model`、`sa_model_config` 构成模型治理体系
- `sa_publish_record`、`sa_eval_dataset`、`sa_eval_task`、`sa_eval_result`、`sa_perf_test_task` 构成治理运营闭环

## 6. 物理结构设计（NRSql）

### 6.1 存储选型建议

- 建议基于 NRSql 的 PostgreSQL 等价事务表能力承载主业务数据
- 主数据表、低频变更表优先启用强约束
- 高频写入事实表优先采用轻外键策略
- JSON 字段统一优先使用 `jsonb`
- 大文本字段统一使用 `text`
- 会话消息、调用日志、执行步骤、运行指标、评测结果等高增长表预留分区或归档策略

### 6.2 命名规范

- 表名保持 `sa_` 前缀
- 主键统一为 `id bigint`
- 业务主键统一使用 `varchar(64)` 或 `varchar(100)`
- 业务编码统一使用 `xxx_code`
- JSON 或快照字段统一保持 `_snapshot`、`_config`、`metadata` 命名
- 索引命名保持 `idx_xxx`
- 唯一约束命名保持 `uk_xxx`
- 主键约束命名可使用 `pk_xxx`

### 6.3 已有表例外说明

已有存量表在 NRSql 版中不强制重构其逻辑标识：

- `users.ID`、`user_info.USER_ID`、`user_additional_info.user_id`、`user_login.USER_ID`、`user_sign.user_id` 继续使用字符型业务主键
- `priv_group.id`、`priv_role.id`、`priv_permission.id`、`priv_menu_resource.id`、`priv_menu_access.per_id` 继续使用字符型主键
- `priv_group_role_relation`、`priv_role_permission_relation`、`priv_user_group_relation` 继续保留联合主键
- `smc_application.application_id`、`smc_service.id`、`smc_instance.instance_id` 保持现有标识体系

如果这些历史表已经存在于 NRSql，则应以现网表结构为准，不重复建模；如果尚未落库，则建议按“保留业务标识类型不变”的原则迁移。

## 8. 关键索引设计

NRSql 版索引策略与 MySQL 版一致，但索引声明方式改为独立 `create index`。重点保留以下索引：

- `sa_application(type, scene_type, status)`
- `sa_application_version(agent_id, version)`
- `sa_session(user_id, gmt_last_active)`
- `sa_session_message(session_id, seq_no)`
- `sa_task(session_id, gmt_start)`
- `sa_task(agent_id, agent_version, status, gmt_start)`
- `sa_execution_step(task_id, step_no)`
- `sa_memory_long_term(memory_library_id, agent_id, user_id, expired_at)`
- `sa_publish_record(asset_type, asset_id, asset_version, gmt_create)`
- `sa_invoke_log(task_id, gmt_create)`
- `sa_runtime_metric(target_type, target_id, metric_name, collect_time)`
- `sa_resource_acl(resource_id, subject_type, subject_id, permission_type)`
- `sa_tag_binding(target_type, target_id, status)`

索引收敛原则保持不变：

- 单表索引优先控制在 `3~5` 组以内
- 低选择性字段不单列建索引
- 高频写入表优先保留“唯一键 + 核心复合索引”

## 9. 落库实施建议

### 9.1 建表顺序建议

1. 先建历史复用基础表或确认其已存在
2. 再建主数据表
3. 再建版本表和绑定表
4. 再建运行态表
5. 最后建治理观测表、索引、注释、触发器

### 9.2 `gmt_modified` 实现建议

- 主数据表：推荐触发器维护
- 高频运行表：推荐应用层维护
- ORM 层如支持自动填充，可作为统一策略

### 9.3 JSON 字段实现建议

- NRSql 统一使用 `jsonb`
- 仅在纯大文本内容场景使用 `text`
- 对需要筛选的 JSON 内部属性，仍建议冗余为结构化字段
- 如后续需要 JSON 路径查询或 GIN 类索引，可直接按 PostgreSQL 能力扩展

### 9.4 外键策略

- 基础主数据表、低频变更表可启用强外键
- 运行时事实表、日志表、指标表不建议建立过多强外键
- 对轻外键场景，必须补充业务索引与数据清理策略

### 9.5 归档与分区建议

以下表建议优先考虑按时间归档或分区：

- `sa_session_message`
- `sa_task`
- `sa_execution_step`
- `sa_invoke_log`
- `sa_runtime_metric`
- `sa_eval_result`
- `sa_memory_hit_record`

## 10. 迁移差异总结

相较于 MySQL 版，NRSql 版的主要变化集中在物理层：

- `auto_increment` 改为 PostgreSQL 风格 `identity`
- `unsigned` 取消，统一为有符号 `bigint`
- `datetime` 优先统一为 `timestamp`
- `json` 统一收敛为 `jsonb`
- `on update current_timestamp` 改为触发器或应用层维护
- `engine`、`charset`、内联 `comment` 语法移除
- 普通索引从内联 `key` 改为独立 `create index`

业务域划分、表职责、主从关系、唯一性设计和权限模型保持不变。

## 11. 后续输出建议

如果进入 NRSql 落地阶段，建议按以下顺序继续输出：

1. NRSql 版核心表 DDL
2. NRSql 版运行态高频表 DDL
3. NRSql 版治理运营表 DDL
4. `gmt_modified` 触发器脚本
5. MySQL 到 NRSql 的字段映射核对清单

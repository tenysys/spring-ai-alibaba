# SophicAgent 数据库设计

## 1. 数据库系统说明

### 1.1 采用的数据库系统
- 事务型业务数据采用 `MySQL 8.x`，用于承载账号权限、应用配置、运行任务、资源管理、数据源元数据、治理审计等核心关系型数据。
- 关系型数据库作为系统主数据源，重点保证事务一致性、结构化查询能力、版本化管理能力和工程交付成熟度。
- 对于知识向量、全文检索、模型 embedding 等非关系型能力，数据库设计中通过业务字段保存引用关系，不直接在本设计中展开底层向量库实现。

### 1.2 采用 MySQL 的原因
- 生态成熟，便于与现有 Java/Spring Boot 技术栈集成。
- 支持事务、索引、JSON 字段、分库分表扩展和运维监控体系。
- 适合承载应用配置、运行态记录、审计日志、统计汇总和元数据管理等结构化场景。
- 与当前 SophicAgent 的表结构设计和多租户模式匹配度高。

## 2. 资源与运行要求

### 2.1 硬盘要求
- 系统需要同时存储业务配置数据、运行任务记录、日志审计、统计汇总和数据源元数据，磁盘容量应按业务规模预留。
- 开发和测试环境建议预留 `100 GB` 以上磁盘空间。
- 生产环境建议按以下维度估算容量：
- 应用配置与资源元数据：占用相对稳定。
- 运行时任务、步骤、调用日志、审计日志：增长最快，应作为主要容量规划对象。
- 数据源字段、关系、语义配置：当接入较多商用库和统一模型时增长明显。
- 长期记忆、评测结果、压测结果：属于扩展增长数据。
- 生产环境建议配置可扩展存储，并配套归档与清理策略，避免日志和运行记录无限增长。

### 2.2 内存要求
- MySQL 实例内存主要用于 buffer pool、连接管理、排序、临时表和热点索引缓存。
- 开发环境建议 `4 GB` 以上可用内存。
- 测试环境建议 `8 GB` 以上可用内存。
- 生产环境建议 `16 GB` 及以上，并根据以下场景继续扩容：
- 高并发任务调度与状态查询。
- 调用日志、审计日志、统计报表的聚合查询。
- 数据源字段和语义配置的大批量检索。
- 多租户并发访问下的热点表索引缓存。

### 2.3 网络带宽要求
- 应用服务与数据库之间需保证低延迟、稳定连接。
- 开发和测试环境建议部署在同一内网环境。
- 生产环境建议应用服务与数据库部署在同一机房或低延迟专网中。
- 当存在以下场景时，应重点评估网络带宽和抖动：
- 高频任务写入 `task`、`execution_step`、`invoke_log` 等运行表。
- 监控、统计、审计类页面并发查询。
- 数据源元数据同步、大批量语义配置生成与导入导出。
- 长期记忆、评测、压测任务集中写入。

### 2.4 效率与性能要求
- 业务主链路表应通过联合索引支撑常用查询，如任务、步骤、调用日志、运行指标、知识文档、数据源字段。
- 运行时写入操作应尽量采用批量插入、异步落库或分级落库策略，避免对在线请求造成阻塞。
- 日志、审计、统计、评测等分析型查询应优先走汇总表、分页查询或异步报表生成机制，避免直接扫描全量明细表。
- 对大表应建立归档、冷热分层和定期清理机制。
- 涉及 JSON 字段的查询不应作为高频主查询路径，关键检索条件应落为普通字段并建立索引。

## 3. 其他限制条件

### 3.1 安全限制
- 数据库账户应按环境和服务拆分权限，禁止业务服务使用高权限账户。
- 敏感字段如连接密码、认证信息、密钥快照等应加密或密文存储，例如 `password_cipher`、`credential`、`auth_config`。
- 审计类数据应具备防篡改和归档机制，满足问题追踪和责任界定要求。
- 数据访问应通过业务服务层统一控制，不允许智能体、工具或外部模块直接绕过服务访问数据库。

### 3.2 容量与归档限制
- `sophic_agent_task`、`sophic_agent_execution_step`、`sophic_agent_invoke_log`、`sophic_agent_audit_event`、`sophic_agent_runtime_metric`、`sophic_agent_eval_result` 等表为高增长表。
- 对高增长表需设计保留周期、归档策略和历史清理策略。
- 对长期保留数据建议按时间或工作空间维度归档，必要时拆分为在线库和历史库。

### 3.3 一致性限制
- 核心配置数据如应用版本、工作流版本、绑定关系、权限关系应保证事务一致性。
- 运行态数据允许在高并发场景下采用“最终一致 + 补偿修复”策略，例如统计汇总、监控指标、压测结果等。
- 跨系统同步的数据，如 MCP 服务、Dify 知识库、外部数据源元数据，应通过同步任务和状态字段管理一致性，不强依赖分布式事务。

### 3.4 运维限制
- 必须具备定期备份、恢复验证、主备切换和容量监控能力。
- 生产环境应开启慢 SQL 日志、连接监控和基础性能监控。
- 数据库表结构变更应采用版本化脚本管理，并与应用发布版本同步。

## 4. 各模块如何使用/访问数据库

### 4.1 身份权限模块
- 使用表：`sophic_agent_account`、`sophic_agent_workspace`、`sophic_agent_api_key`、`sophic_agent_role`、`sophic_agent_permission`、`sophic_agent_role_permission`、`sophic_agent_account_role`
- 使用方式：
- 账号登录、工作空间切换、API 鉴权、角色权限判定均通过服务层访问上述表。
- 权限校验优先读取角色和权限映射，必要时可在缓存层做短期缓存。

### 4.2 应用管理模块
- 使用表：`sophic_agent_application`、`sophic_agent_application_version`
- 使用方式：
- 应用列表、详情、版本历史、版本差异、导出 DSL 等功能通过查询应用主表和版本表实现。
- 应用的最新版本、状态、标签、场景分类等信息以主表聚合字段为主，减少频繁扫描版本明细。

### 4.3 高代码服务模块
- 使用表：`sophic_agent_high_code_service`、`sophic_agent_high_code_service_version`
- 使用方式：
- 服务注册、版本管理、制品下载、部署信息查询通过主表和版本表完成。
- 运行控制记录可以和运行时、部署计划表结合使用。

### 4.4 设计器模块
- 使用表：`sophic_agent_workflow_definition`、`sophic_agent_workflow_version`、`sophic_agent_workflow_node`、`sophic_agent_workflow_edge`、`sophic_agent_application_binding`、`sophic_agent_application_binding_item`
- 使用方式：
- 设计器通过流程定义、节点、连线表保存画布结构，通过应用绑定表保存模型、知识库、工具、记忆库、数据源等依赖关系。
- 对具体 MCP 工具、表、字段、概念等细粒度选择，通过绑定明细表保存。
- 设计器的发布与版本保存优先采用“版本快照 + 明细结构”的组合模式。

### 4.5 模型管理模块
- 使用表：`sophic_agent_model_provider`、`sophic_agent_model`
- 使用方式：
- 模型供应商、模型接入配置、连接信息、运行参数通过模型域表统一管理。
- 运行时在装载应用配置时读取模型配置，不直接写入模型表。

### 4.6 运行时模块
- 使用表：`sophic_agent_runtime_event`、`sophic_agent_task`、`sophic_agent_execution_plan`、`sophic_agent_execution_step`、`sophic_agent_task_queue`
- 使用方式：
- 外部事件进入系统后写入运行事件表，任务执行主链路写入任务、执行计划、执行步骤和调度队列表。
- 在线请求应避免在高频路径进行复杂关联查询，优先按 `task_id`、`agent_id`、`status` 等索引字段访问。
- 对步骤级明细查询和流程跟踪应分页或按任务聚合读取。

### 4.7 知识库模块
- 使用表：`sophic_agent_knowledge_base`、`sophic_agent_knowledge_document`、`sophic_agent_knowledge_chunk`
- 使用方式：
- 知识库主数据、文档导入状态、分片管理和索引状态由关系型数据库管理。
- 向量检索系统或外部知识服务的真实索引实体通过 `vector_id`、配置字段或扩展元数据建立引用关系。

### 4.8 工具与 MCP 模块
- 使用表：`sophic_agent_tool`、`sophic_agent_tool_version`、`sophic_agent_tool_debug_record`、`sophic_agent_mcp_server`、`sophic_agent_resource`
- 使用方式：
- 工具主信息、版本协议、调试记录和 MCP 服务接入信息由关系型数据库统一管理。
- 资源表用于统一登记工具、知识库、MCP 服务、数据源、应用等资产，方便能力中心与设计器统一检索。

### 4.9 记忆模块
- 使用表：`sophic_agent_memory_short_term`、`sophic_agent_memory_working`、`sophic_agent_memory_long_term`、`sophic_agent_memory_library`、`sophic_agent_memory_rule`、`sophic_agent_memory_hit_record`
- 使用方式：
- 短期记忆按会话写入，工作记忆按任务写入，长期记忆按用户、记忆库和规则维度管理。
- 长期记忆召回时可通过记忆命中记录保存命中结果与相似度，供后续优化和效果评估使用。

### 4.10 数据源与语义模块
- 使用表：`sophic_agent_datasource`、`sophic_agent_datasource_table`、`sophic_agent_datasource_field`、`sophic_agent_datasource_relation`、`sophic_agent_datasource_semantic_model`
- 使用方式：
- 数据源主表保存连接与同步配置，表/字段/关系/语义模型表保存同步后的元数据和人工补充配置。
- 数据源配置页、语义配置页、逻辑外键配置页均通过这些表访问数据。
- 对外部数据库的实时访问不应直接依赖这些元数据表，而是由统一数据访问服务结合这些元数据完成解析和路由。

### 4.11 治理观测模块
- 使用表：`sophic_agent_invoke_log`、`sophic_agent_audit_event`、`sophic_agent_runtime_metric`、`sophic_agent_alarm_rule`、`sophic_agent_alarm_record`、`sophic_agent_fault_record`、`sophic_agent_fault_process_record`
- 使用方式：
- 调用链路、审计事件、运行指标、告警和故障处理均落在治理观测域表中。
- 监控大盘、日志审计页、调用统计页优先读取明细表或汇总表组合，不建议直接在页面层进行复杂聚合。

### 4.12 发布与部署模块
- 使用表：`sophic_agent_publish_record`、`sophic_agent_runtime_config_history`、`sophic_agent_integration_endpoint`、`sophic_agent_integration_record`、`sophic_agent_deploy_plan`
- 使用方式：
- 发布记录保存应用、工具和高代码服务的发布快照。
- 接入点和集成调用记录用于外部系统接入管理。
- 部署计划和运行配置历史用于部署、回滚和配置审计。

### 4.13 评估与压测模块
- 使用表：`sophic_agent_eval_dataset`、`sophic_agent_eval_dataset_item`、`sophic_agent_eval_task`、`sophic_agent_eval_result`、`sophic_agent_perf_test_task`
- 使用方式：
- 评测集管理维护测试问题和参考答案。
- 评测任务和结果表保存自动评测、人工评测过程和结果。
- 性能评测任务表保存压测配置和压测结果摘要。

## 5. 结论
- SophicAgent 当前数据库设计以 `MySQL 8.x` 为核心事务数据库，满足多租户、配置管理、运行记录、能力资产、数据源元数据、治理审计、发布评估等场景。
- 对高增长运行数据和分析型数据，应重点配套索引、汇总、归档和容量治理策略。
- 各模块必须通过服务层统一访问数据库，禁止绕过服务直接访问底层表，以保证权限、安全、审计和一致性。

## 6. 概念结构设计

### 6.1 设计目标
- 将与系统相关的数据按业务职责进行分解，再按统一业务主键和租户维度进行组织，形成可扩展、可治理、可追踪的数据库全局逻辑结构。
- 概念结构设计以领域对象为核心，不直接面向页面或接口，而是围绕系统长期稳定的核心实体进行建模。

### 6.2 核心概念实体
- 身份权限实体：账号、工作空间、角色、权限、API Key。
- 应用设计实体：应用、应用版本、高代码服务、高代码服务版本、模型供应商、模型、工作流定义、工作流版本、工作流节点、工作流连线。
- 运行执行实体：运行事件、任务、执行计划、执行步骤、调度队列。
- 能力资产实体：知识库、知识文档、知识分片、工具、工具版本、工具调试记录、MCP 服务、统一资源、短期记忆、工作记忆。
- 数据源语义实体：数据源、表元数据、字段元数据、逻辑关系、语义模型。
- 治理观测实体：调用日志、审计事件、运行指标、告警规则、告警记录、故障记录、故障处理记录。
- 增强治理实体：长期记忆、记忆库、记忆规则、记忆命中记录、调用日统计、限流规则、并发配额、高可用节点、主备切换记录、运行配置历史、接入点、集成记录、部署计划、发布记录、评测集、评测样本、评测任务、评测结果、压测任务。

### 6.3 全局概念关系
- 一个工作空间可拥有多个账号关系、应用、工具、知识库、数据源、任务、告警、评测任务等业务对象。
- 一个应用可存在多个版本，一个版本可绑定多个模型、工具、知识库、数据源、记忆库或 MCP 服务。
- 一个工作流定义可演化为多个版本，一个版本包含多个节点和多个连线。
- 一个任务可对应一个执行计划，一个执行计划可拆分为多个执行步骤。
- 一个知识库可包含多个文档，一个文档可拆分为多个分片。
- 一个数据源可包含多张表，一张表可包含多个字段，并可定义多条逻辑关系和语义配置。
- 一个记忆库可包含多条记忆规则和多条长期记忆记录。
- 一个评测集可包含多个样本，一个评测任务可产出多条评测结果。

### 6.4 建模表达建议
- 关系数据库建议采用 E-R 图表达概念实体及其一对一、一对多、多对多关系。
- 若后续扩展到对象化配置建模或复杂设计器对象模型，可补充使用 UML 类图、对象图描述对象层结构。
- 当前数据库设计以关系型建模为主，推荐以 E-R 图作为主表达形式，UML 作为设计器和流程对象的补充说明形式。

## 7. 逻辑结构设计

### 7.1 逻辑分层
- 基础身份层：承载账号、权限、租户和安全控制。
- 应用配置层：承载应用、版本、工作流、模型和绑定关系。
- 运行执行层：承载事件、任务、计划、步骤和调度信息。
- 能力资产层：承载知识、工具、MCP、记忆和统一资源登记。
- 数据源建模层：承载数据源连接信息、表字段元数据、逻辑关系和语义映射。
- 治理分析层：承载日志、审计、监控、统计、告警、故障、评测和发布信息。

### 7.2 关键字与主标识设计
- 技术主键统一为 `id`，用于数据库内部关联和高性能索引。
- 业务主键统一采用 `xxx_id`，用于跨表关联和外部系统引用。
- 业务编码统一采用 `xxx_code`，用于唯一业务识别、页面检索和配置装载。
- 多租户统一通过 `workspace_id` 进行逻辑隔离。
- 版本化对象统一使用 `version` 标识版本，主表维护 `latest_version` 作为当前有效版本快速入口。

### 7.3 关键表与关联属性
- `sophic_agent_application` 与 `sophic_agent_application_version` 通过 `agent_id` 关联，形成应用与版本的 1-N 关系。
- `sophic_agent_application_version` 与 `sophic_agent_workflow_definition` 通过 `workflow_definition_id` 形成配置装载关系。
- `sophic_agent_application_binding` 通过 `agent_id + agent_version` 与应用版本关联，通过 `resource_type + resource_id` 与外部能力资产建立逻辑绑定。
- `sophic_agent_application_binding_item` 通过 `binding_id` 关联绑定关系，用于保存 MCP 工具、表、字段、概念等细粒度明细。
- `sophic_agent_workflow_version` 通过 `definition_id + version` 与 `sophic_agent_workflow_node`、`sophic_agent_workflow_edge` 关联，形成流程图结构。
- `sophic_agent_task` 通过 `task_id` 关联 `sophic_agent_execution_plan` 和 `sophic_agent_execution_step`，形成运行执行链。
- `sophic_agent_knowledge_base` 通过 `kb_id` 关联 `sophic_agent_knowledge_document`，再由 `doc_id` 关联 `sophic_agent_knowledge_chunk`。
- `sophic_agent_datasource` 通过 `datasource_id` 关联表、字段、逻辑关系和语义模型，形成完整数据源元数据链路。
- `sophic_agent_memory_library` 通过 `memory_library_id` 关联 `sophic_agent_memory_rule` 和 `sophic_agent_memory_long_term`。
- `sophic_agent_eval_dataset` 通过 `dataset_id` 关联 `sophic_agent_eval_dataset_item`，`sophic_agent_eval_task` 通过 `eval_task_id` 关联 `sophic_agent_eval_result`。

### 7.4 数据分解与合并原则
- 稳定主数据与高频运行数据分离，如应用主表与任务执行表分离。
- 版本快照与当前主对象分离，如应用主表和版本表、工具主表和版本表分离。
- 主关系与明细选择分离，如绑定表和绑定明细表分离。
- 主元数据与扩展语义配置分离，如数据源表字段元数据与语义模型分离。
- 明细日志与汇总统计分离，如调用日志和调用日统计分离。

## 8. 物理结构设计

### 8.1 表组织方式
- 所有业务表统一采用 InnoDB 引擎，满足事务、行级锁和崩溃恢复要求。
- 字符集统一采用 `utf8mb4`，满足中文、符号和扩展字符存储要求。
- 高频访问表与高增长表采用独立索引设计，避免全表扫描。
- 配置快照、规则、扩展元数据统一使用 `JSON` 字段承载，平衡灵活性与结构稳定性。

### 8.2 索引设计
- 主业务链路表采用组合索引支撑常见访问路径。
- 任务主链路重点索引：`(workspace_id, agent_id, status, gmt_create)`。
- 执行步骤重点索引：`(task_id, step_no)`。
- 调用日志重点索引：`(workspace_id, task_id, gmt_create)` 和 `trace_id`。
- 运行指标重点索引：`(workspace_id, metric_name, collect_time)`。
- 知识文档重点索引：`(workspace_id, kb_id, index_status, status)`。
- 数据源字段重点索引：`(workspace_id, datasource_id, table_id)`。
- 长期记忆重点索引：`(workspace_id, memory_library_id, user_id, status, gmt_create)`。
- 发布与评测重点索引：`(workspace_id, asset_type, asset_id, status)`、`(workspace_id, target_type, target_id, status)`。

### 8.3 缓冲区与访问特性
- 数据库侧应重点依赖 InnoDB Buffer Pool 缓存热点表和热点索引页。
- 对高频读取的基础数据，如应用主信息、模型配置、角色权限、资源登记，可在应用层叠加本地缓存或分布式缓存，减轻数据库压力。
- 对高频写入的运行表、日志表和指标表，建议通过异步写入、批量写入或消息削峰手段降低瞬时写压力。
- 对统计类和报表类页面，建议优先访问汇总表或离线聚合结果，避免与在线事务表争抢缓冲区资源。

### 8.4 存储过程与数据库侧逻辑
- 当前设计原则上不依赖复杂存储过程承载业务逻辑，核心业务逻辑放在应用服务层实现，便于版本管理和服务治理。
- 数据库侧可保留轻量级存储过程或定时任务用于辅助运维场景，如历史归档、批量清理、统计预聚合、异常修复。
- 若后续引入数据库事件调度或存储过程，应限定在“数据维护型逻辑”范围内，不承载跨模块主业务流程。

### 8.5 分区、归档与扩展
- 高增长表如任务、执行步骤、调用日志、审计事件、运行指标、评测结果，建议按时间维度进行分区或归档。
- 超大租户场景下，可按 `workspace_id` 或时间范围进行逻辑分库分表扩展。
- 历史数据建议迁移到归档库或分析库，在线库保留近期高频访问数据。

### 8.6 物理设计表达建议
- 概念结构建议使用 E-R 图展示实体、主键、外键和基数关系。
- 逻辑结构建议补充领域分层图和关键表关联图。
- 物理结构建议补充表清单、索引清单、容量估算表、归档策略表和部署拓扑图。

## 11. 补充说明
- 分区策略应结合 MySQL 版本、运维规范和真实数据量评估后实施，不建议在数据量较小阶段过早复杂化。
- 归档策略应与审计要求、故障追溯要求和业务查询需求统一设计。
- 对需要长期保留但查询频率较低的数据，优先采用“在线明细表 + 历史归档表/历史库”的方式管理。

## 12. 数据库运行设计

### 12.1 硬件环境设计
- 开发环境建议采用单实例部署，满足本地开发、联调和基础功能验证。
- 测试环境建议采用独立数据库实例，避免与开发环境共用数据和配置。
- 生产环境建议使用独立数据库服务器或云数据库实例，部署在高可靠硬件环境中。
- 推荐硬件设计原则：
- CPU：满足高并发查询、批量写入、索引维护和统计聚合需求，生产环境建议至少 8 核起步。
- 内存：优先保障 InnoDB Buffer Pool、热点索引缓存和连接池开销，生产环境建议 16 GB 起步，中大型场景建议 32 GB 及以上。
- 磁盘：优先采用 SSD 或 NVMe 高性能存储，重点保障运行表、日志表和索引写入性能。
- 磁盘冗余：建议使用 RAID 或云盘多副本机制，避免单盘故障导致数据不可用。

### 12.2 软件环境设计
- 数据库系统建议采用 `MySQL 8.x`。
- 存储引擎统一采用 `InnoDB`。
- 字符集统一采用 `utf8mb4`。
- 数据库连接建议通过应用侧连接池管理，如 HikariCP。
- 生产环境建议启用以下基础能力：
- 慢 SQL 日志。
- 二进制日志 `binlog`。
- 基础性能监控与告警。
- 定期统计信息更新与索引健康检查。
- 参数设计原则：
- `innodb_buffer_pool_size` 根据实例内存设置为核心参数。
- `max_connections` 按应用并发与连接池规模统一规划。
- `binlog_format`、`sync_binlog`、`innodb_flush_log_at_trx_commit` 根据一致性要求设置。

### 12.3 网络环境设计
- 应用服务、数据库、缓存、消息系统建议部署在同一专有内网环境。
- 数据库应避免直接暴露在公网。
- 生产环境建议数据库与核心应用部署在同机房、同可用区或低延迟专网环境中。
- 网络设计重点：
- 保证数据库连接稳定，避免跨广域网高延迟访问。
- 对数据库访问开放最小化白名单，仅允许应用服务、运维堡垒机和备份节点访问。
- 复制链路、备份链路与业务链路宜分离或逻辑隔离，避免相互影响。

### 12.4 备份与恢复设计

#### 12.4.1 备份策略
- 采用“全量备份 + 增量日志备份”组合策略。
- 全量备份建议每日或每周定时执行，具体周期依据数据增长速度和恢复目标确定。
- 增量备份主要依赖 `binlog`，实现时间点恢复。
- 关键配置数据、权限数据、应用版本数据、工作流定义、发布记录、评测数据应纳入重点备份范围。
- 备份文件应保存在独立存储介质或独立备份空间中，避免与主库共盘。

#### 12.4.2 恢复策略
- 支持整库恢复、单库恢复、按时间点恢复和特定表恢复。
- 生产环境应定期执行恢复演练，验证备份可用性和恢复时长。
- 恢复时优先恢复主数据和配置数据，再恢复日志与历史类数据。
- 对审计、故障、评测等历史数据可根据业务优先级分阶段恢复。

#### 12.4.3 恢复目标建议
- 核心事务数据建议以较小 RPO 为目标，尽量减少数据丢失窗口。
- 核心在线业务建议以较短 RTO 为目标，缩短主流程恢复时间。
- 日志、统计、评测类数据可适当放宽恢复时效，但需保证数据完整性。

### 12.5 双机/多机热备设计

#### 12.5.1 双机热备
- 中小规模生产环境建议采用主从或主备部署。
- 主库承载写请求和主要读请求，从库用于热备、只读查询和故障接管。
- 同步方式可采用 MySQL 原生复制机制，建议至少做到半同步或可靠复制策略。

#### 12.5.2 多机高可用
- 中大型场景建议采用“一主多从”或高可用集群方案。
- 读写分离场景中，可将统计、审计、报表、评测等偏分析型查询分流到只读副本。
- 配置自动故障检测和主从切换机制，切换过程需与应用连接管理协同。

#### 12.5.3 热备设计原则
- 主备节点间保持数据实时或准实时同步。
- 备用节点应具备与主节点等价的表结构、索引和关键参数配置。
- 切换后需保证应用能够快速更新连接信息，避免长时间不可用。
- 切换过程应保留审计记录和故障处理记录。

### 12.6 数据库访问安全性设计

#### 12.6.1 账号与权限控制
- 按环境分离数据库账号，开发、测试、生产环境不得混用。
- 按服务职责分配最小权限，业务服务只授予必要的读写权限。
- 禁止应用使用数据库管理员账号运行。

#### 12.6.2 网络与访问控制
- 数据库访问应基于内网、白名单、防火墙规则和堡垒机控制。
- 仅允许受信应用节点、运维节点和备份节点接入数据库。
- 数据库管理端口禁止直接暴露到公网。

#### 12.6.3 数据安全
- 敏感信息如密码、密钥、认证配置、访问令牌应加密或密文存储。
- 关键配置变更、权限变更和数据恢复操作应记录审计日志。
- 重要数据导出操作应纳入审批或审计范围。

#### 12.6.4 连接安全
- 应用与数据库之间建议启用 TLS 或专网加密传输能力。
- 连接池配置应限制空闲连接和异常连接重试，防止资源耗尽。
- 对异常来源、暴力访问和高频失败连接应具备检测和拦截能力。

#### 12.6.5 安全运维
- 定期轮换数据库访问密码和证书。
- 定期检查高权限账号、过期账号和异常授权。
- 定期审查慢 SQL、失败登录、异常连接和越权访问行为。
